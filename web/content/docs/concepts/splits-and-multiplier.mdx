When a company makes a stock split or pays a dividend, the [B20](/docs/help/glossary#b20) token that tracks the stock changes a number called the [uiMultiplier](/docs/help/glossary#uimultiplier). This page explains what that number is, why a change to it makes the [vault](/docs/help/glossary#vault) stop trading in that one stock for a while, how the vault notices a change by itself, and what it does when the token does not answer. The rules are built and have been exercised with a mock token in unit tests. On the [Base](/docs/help/glossary#base) mainnet fork the vault read the real multiplier but never saw it change, and nothing is deployed.

## What the multiplier is

A B20 stock token publishes `uiMultiplier()` as a [WAD](/docs/help/glossary#wad) number, a fixed-point value scaled so that `1e18` means 1.0. The vault reads it through the `IB20Asset` interface, together with `effectiveAt()`, which it uses for scheduled changes (see [Scheduled changes](#scheduled-changes)). On the fork, at block <Fact name="forkBlock" />, NVDAc reports <Fact name="nvdaUiMultiplier" />, a little above 1.

The token also has a display balance, `balanceOfUI`. The vault never values anything with it. It values the [raw amount](/docs/help/glossary#raw-amount) that `balanceOf` returns, and it reads the [Chainlink equity feed](/docs/help/glossary#chainlink-equity-feed) answer as the price of one whole token, `10 ** decimals()` raw units, with the multiplier already applied. The design spec records why: the feed matched Coinbase's NAV price, so the multiplier must not be applied a second time. The value of a holding is the raw amount times the price (<Fact name="priceDecimals" />), divided down to USDC units (<Fact name="usdcDecimals" />):

```solidity title="contracts/src/MandateVault.sol#L504-L507"
    /// @dev raw stock amount x 8-decimal price -> USDC (6 decimals)
    function _valueUsd(address token, uint256 raw, uint256 price8) internal view returns (uint256) {
        return raw * price8 / 10 ** (uint256(IB20Asset(token).decimals()) + 2);
    }
```

No part of this reads the multiplier. The multiplier matters to the vault for one reason: whether the raw balance and the feed price still agree about it.

## Why a change is dangerous

The vault assumes that the feed already includes the multiplier. The README lists this as a known limitation: it was checked while the multiplier was close to 1, and it has not been observed across a real split. So these docs cannot show what the feed and the token do in the hours around one.

What the vault can say is which of its readings depend on the multiplier being settled. The value of a holding is a raw amount times a feed price, and the premium check compares a pool [TWAP](/docs/help/glossary#twap), averaged over <Fact name="mandate.twapWindowSec" />, with the feed price. The README gives the reason in one line: values computed across the change are wrong. The vault does not try to work out when the feed and the pool have caught up. It stops trading in that stock, then waits out a cooldown.

<Callout type="fork" title="Fork-measured, not a split">

The multiplier above is one reading, taken on the fork at block <Fact name="forkBlock" />. It shows that NVDAc's multiplier was a little above 1 on that day. It says nothing about what happens across a split: no change was observed on the fork, and the tests on this page change a mock token's multiplier instead.

</Callout>

## How the vault notices

The vault keeps a snapshot of each stock's multiplier, `lastMultiplier`, and the time it last recorded a change, `multiplierChangedAt`. Both are public mappings. The snapshot is taken when a stock is configured with a market, and the read there is not wrapped, so a token whose `uiMultiplier()` [reverts](/docs/help/glossary#revert) cannot be configured that way.

```solidity title="contracts/src/MandateVault.sol#L705-L710"
        if (market) {
            uint256 cur = IB20Asset(token).uiMultiplier();
            // First snapshot (last == 0) starts no cooldown; re-applying must not silently absorb a later change.
            if (lastMultiplier[token] == 0) lastMultiplier[token] = cur;
            else _recordMultiplier(token, cur);
        }
```

The first snapshot starts no cooldown (`test_firstSnapshotStartsNoCooldown`). Applying a stock's settings again records a difference as a change, so applying them cannot hide one (`test_reapplyingTokenConfigDoesNotAbsorbMultiplierChange`).

After that the vault records changes in two places: at the start of every `execute` for the intent's token, and in `syncMultiplier`, which anyone can call. Only a stock with a market is tracked, which means one that is allowed, or that still has a feed or a pool. An [exit-only](/docs/help/glossary#exit-only) stock is tracked too.

```solidity title="contracts/src/MandateVault.sol#L640-L653"
    function _syncMultiplier(address token) internal {
        // A reverting uiMultiplier() must not revert execute(); GuardLib then fails closed with MULTIPLIER_COOLDOWN.
        try IB20Asset(token).uiMultiplier() returns (uint256 cur) {
            _recordMultiplier(token, cur);
        } catch {}
    }

    function _recordMultiplier(address token, uint256 cur) internal {
        uint256 last = lastMultiplier[token];
        if (cur == last) return;
        multiplierChangedAt[token] = block.timestamp;
        lastMultiplier[token] = cur;
        emit MultiplierChangeDetected(token, last, cur);
    }
```

An unchanged value records nothing. A changed one is stored, stamped with the block time and announced with `MultiplierChangeDetected(token, oldMultiplier, newMultiplier)`. The token is an indexed topic, so a log filter can follow one stock.

The check does not wait for the snapshot to catch up. It compares the token's current multiplier with the snapshot every time it runs, so a changed multiplier blocks the stock as soon as the token reports it, before anyone records the change. Recording then starts the cooldown clock. In [live mode](/docs/help/glossary#live-mode) the agent is built to send `syncMultiplier` for any stock whose multiplier differs from the snapshot, before it proposes anything ([Step 1 of a round](/docs/get-started/how-a-decision-is-made#step-1-read-the-vault)).

Credit actions show why recording matters. A `BORROW` or a `REPAY` must name USDC, and `execute` records only the intent's token, so a valid one records nothing for the stocks held as collateral. After a change in one of them, `BORROW`, and `WITHDRAW_COLLATERAL` against debt, are refused with `MULTIPLIER_COOLDOWN` once the earlier checks pass ([The cooldown](#the-cooldown)). The vault's cooldown clock does not start until `syncMultiplier`, an `execute` that names that stock, or an `applyTokenConfig` for it records the change, so waiting alone does not clear the block. Anyone can call `syncMultiplier` ([Anyone can sync](#anyone-can-sync)), and the agent is built to call it as above.

## The cooldown

Check 6 of [the nine checks](/docs/concepts/nine-checks#6-stable-multiplier) returns `MULTIPLIER_COOLDOWN` while `GuardLib.multiplierBlocked` says true. The cooldown is the mandate's `multiplierCooldown`, <Fact name="mandate.multiplierCooldownSec" /> by default ([the mandate](/docs/concepts/mandate#multipliercooldown)). The function has two halves. The first compares the snapshot and checks the vault's own clock:

```solidity title="contracts/src/GuardLib.sol#L123-L131"
        if (last != 0) {
            try t.uiMultiplier() returns (uint256 m) {
                if (m != last) return true;
            } catch {
                return true;
            }
        }
        // forge-lint: disable-next-line(block-timestamp)
        if (changedAt != 0 && block.timestamp < changedAt + cooldown) return true;
```

- With a snapshot set, the token's current multiplier must equal it, and the read must work.
- A change that the vault recorded less than the cooldown ago blocks the stock.

The cooldown counts from when the vault records the change, because the vault only knows when it noticed. Until someone records it, the first branch keeps blocking with no time limit. `test_multiplierChangeStartsCooldown` changes a mock token's multiplier, gets `MULTIPLIER_COOLDOWN`, and gets an allowed buy once the cooldown has passed.

The same function guards more than trades. A `BUY` and a `SELL` meet it as check 6, and a `SELL` of an exit-only stock is still guarded (`test_exitOnlyTokenIsStillMultiplierGuarded`). A `BORROW`, and a `WITHDRAW_COLLATERAL` against debt, meet it through `GuardLib.collateralHealthy` for every stock supplied as collateral (`test_collateralMultiplierChangeBlocksBorrow`). `SUPPLY`, `REPAY`, `PAY_EXPENSE` and a withdrawal with no debt do not read the multiplier. [Refusal codes](/docs/concepts/refusal-codes#multiplier_cooldown) lists the actions that can return it.

## Scheduled changes

A token can also announce a change before it happens, through `effectiveAt()`. The second half of the function reads it:

```solidity title="contracts/src/GuardLib.sol#L132-L141"
        uint256 eff = 0;
        try t.effectiveAt() returns (uint256 e) {
            eff = e;
        } catch {
            return true;
        }
        // forge-lint: disable-next-line(block-timestamp)
        if (eff > block.timestamp) return true; // scheduled update pending
        // forge-lint: disable-next-line(block-timestamp)
        return eff != 0 && block.timestamp < eff + cooldown;
```

- An `effectiveAt()` that cannot be read blocks the stock.
- An `effectiveAt()` in the future is a scheduled update that is still pending, so the stock stays blocked until it takes effect.
- A non-zero `effectiveAt()` that is in the past blocks the stock until the cooldown has passed since it.
- Zero means nothing is scheduled. A change that leaves `effectiveAt()` at zero is called "legacy-style" in the tests, and only the snapshot catches it.

`test_multiplierRules` in [GuardLib.t.sol](https://github.com/duongnq2798/maat/blob/main/contracts/test/GuardLib.t.sol) walks these cases against a mock token: a pending update blocks, an update that took effect inside the cooldown blocks, and an update whose cooldown has passed is allowed. `test_pendingMultiplierBlocks` shows the same through the vault.

## Fail closed

Every read of the token on this path is [fail closed](/docs/help/glossary#fail-closed): an answer the vault cannot get counts as the unsafe one.

| Read | If it reverts | Shown by |
| --- | --- | --- |
| `uiMultiplier()` inside the check | The stock is blocked: `MULTIPLIER_COOLDOWN` | `test_revertingUiMultiplierFailsClosed` |
| `effectiveAt()` inside the check | The stock is blocked: `MULTIPLIER_COOLDOWN` | `test_revertingEffectiveAtFailsClosed` |
| `uiMultiplier()` while recording | Nothing is recorded and `execute` does not revert. The check then blocks | `test_revertingUiMultiplierFailsClosedWithoutReverting` |
| `uiMultiplier()` while configuring a stock with a market | The configuration reverts, so the stock is never listed | The fork harness, see below |

The first two tests are in `GuardLib.t.sol`, the third in `MandateVault.t.sol`. For the last row, a comment in the agent's fork harness (`agent/test/integration/anvil.ts`) records the effect: upstream `anvil` answers `decimals()` for a B20 token but reverts on `uiMultiplier()`, so the vault cannot be deployed on it. The fork run uses Base's own Foundry build instead.

## Anyone can sync

`syncMultiplier(token)` has no access check. For a stock without a market it does nothing. For any other it reads the token and records the value as shown above. The README groups it with `notifyRevenue` as functions that anyone can call and that only record state.

- **It cannot choose the value.** The vault reads the multiplier from the token itself.
- **It cannot end a block early.** Recording starts the cooldown, and the stock stays blocked until the cooldown has passed.
- **It cannot extend a block.** A second call sees no difference and returns.
- **It does not need the [executor](/docs/help/glossary#executor), and a pause does not stop it.** Anyone can have a change recorded while the vault is paused.

The mechanism is the same for every stock the vault tracks. [Prices and premium](/docs/concepts/prices-and-premium#assumptions) lists the other assumptions the price checks rest on, and the [MandateVault reference](/docs/reference/mandate-vault) lists every function.
