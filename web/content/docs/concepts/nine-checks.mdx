A `BUY` or a `SELL` moves funds only after it passes up to <Fact name="checksPerTrade" /> checks inside the vault, run in a fixed order (check 9 applies to a `BUY` only).
The first one that fails decides the [refusal code](/docs/concepts/refusal-codes), the vault records it
in a [Decision](/docs/help/glossary#decision) event, and no funds move. Nothing the agent sends can skip a check: the vault runs them
itself, on every `execute` call for a `BUY` or a `SELL`. This page lists the checks in order, says what each one reads, and names the code it returns.

## The order

The vault numbers <Fact name="checksPerTrade" /> checks. Two guards without a number sit in the same order: the pause flag runs
first, and the balance guard runs after check 7. A dot in the first column marks them.

| # | Check | Refuses with | Where |
| --- | --- | --- | --- |
| · | The vault is not paused (every action except `REPAY`) | `VAULT_PAUSED` | `MandateVault._check` |
| 1 | The token is [allowed](/docs/concepts/mandate#allowed) in its per-token settings, its `TokenConfig` (a `SELL` needs only a market) | `TOKEN_NOT_ALLOWED` | `MandateVault._check` |
| 2 | The token's transfers are not paused | `TOKEN_PAUSED` | `GuardLib.tokenPaused` |
| 3 | Every leg of the transfer passes the [B20](/docs/help/glossary#b20) policy registry | `POLICY_BLOCKED` | `GuardLib.transferPathAuthorized` |
| 4 | The market is open for the [mandate](/docs/help/glossary#mandate)'s session | `MARKET_CLOSED` | `GuardLib.marketOpen` |
| 5 | The oracle answer is positive and fresh | `FEED_STALE`, `BAD_PRICE` | `PriceLib.readFeed`, `GuardLib.checkMarket` |
| 6 | The token's multiplier is stable | `MULTIPLIER_COOLDOWN` | `GuardLib.multiplierBlocked` |
| 7 | The pool [TWAP](/docs/help/glossary#twap) is close to the oracle | `PREMIUM_TOO_HIGH`, `BAD_PRICE` | `PriceLib.twapPrice`, `PriceLib.premiumBps` |
| · | The amount is non-zero and covered by the balance | `INSUFFICIENT_BALANCE` | `MandateVault._check` |
| 8 | The notional fits the per-trade and daily caps | `SIZE_LIMIT` | `MandateVault._withinCaps` |
| 9 | After a `BUY`, the stock's weight stays within its cap | `CONCENTRATION` | `MandateVault._weightAfterBuyBps` |

The market checks sit in one function. Checks 2 to 7 are in `GuardLib.checkMarket`; check 1 and the guards around it are in `MandateVault._check`, which calls `checkMarket` in the middle.

```solidity title="contracts/src/GuardLib.sol#L44-L62"
    function checkMarket(MarketCheck memory c) internal view returns (Reason, uint256) {
        IB20Asset t = IB20Asset(c.token);
        if (tokenPaused(c.token)) return (Reason.TOKEN_PAUSED, 0);
        if (!transferPathAuthorized(c)) return (Reason.POLICY_BLOCKED, 0);
        if (!marketOpen(c.calendar, c.sessionMode)) return (Reason.MARKET_CLOSED, 0);

        (bool ok, uint256 oracle, uint256 age) = PriceLib.readFeed(c.feed);
        if (!ok) return (Reason.BAD_PRICE, 0);
        if (age > c.maxStaleness) return (Reason.FEED_STALE, 0);

        if (multiplierBlocked(t, c.lastMultiplier, c.multiplierChangedAt, c.multiplierCooldown)) {
            return (Reason.MULTIPLIER_COOLDOWN, 0);
        }

        (bool tok, uint256 dex) = PriceLib.twapPrice(c.pool, c.token, c.twapWindow);
        if (!tok) return (Reason.BAD_PRICE, 0);
        if (PriceLib.premiumBps(dex, oracle) > c.maxPremiumBps) return (Reason.PREMIUM_TOO_HIGH, 0);
        return (Reason.OK, oracle);
    }
```

Read it top to bottom. Each `if` returns the reason of one check, so the order of the `if` lines is the order of the checks: token paused, transfer policy, market, oracle, multiplier, pool price. The second value it returns is the oracle price, which the vault reuses to value the trade and to compute the slippage floor.

## Why the order matters

Market reasons come first, so a refusal names the outside condition that blocked the trade, not a side
effect of it. On a Saturday the vault reports `MARKET_CLOSED`, not `FEED_STALE`, even when the feed
is also older than `maxStaleness` by then. The balance guard runs after the market checks for the same reason: an empty vault
on a Saturday or a holiday still reports `MARKET_CLOSED`.

Tests pin the order:

- `test_marketReasonTakesPrecedenceOverBalance` shows that a stale feed beats an over-balance buy, and that on a Saturday an empty vault reports `MARKET_CLOSED` for a sell and for a zero-amount buy.
- `test_pauseIsCheckedBeforeMarketHours` shows that a paused token reports `TOKEN_PAUSED` on a Saturday.
- `test_weekendBuyIsRefusedInBothModes` buys at a real weekend block, where the NVDAc feed was last updated on the Friday before, and still gets `MARKET_CLOSED` in both [session modes](/docs/help/glossary#session-mode). It is in [MandateVaultFork.t.sol](https://github.com/duongnq2798/maat/blob/main/contracts/test/fork/MandateVaultFork.t.sol).

## Each check

The tests named below are in [MandateVault.t.sol](https://github.com/duongnq2798/maat/blob/main/contracts/test/MandateVault.t.sol), [GuardLib.t.sol](https://github.com/duongnq2798/maat/blob/main/contracts/test/GuardLib.t.sol) and [PriceLib.t.sol](https://github.com/duongnq2798/maat/blob/main/contracts/test/PriceLib.t.sol). Several checks are [fail closed](/docs/help/glossary#fail-closed): a read that reverts counts as the unsafe answer, so the trade is refused and recorded.

### Guard: the vault is not paused

Reads the vault's `paused` flag, which only the owner can set. When it is set, every action except `REPAY` returns `VAULT_PAUSED` before any other check runs, so repaying debt still works while the vault is stopped. `test_vaultPaused` shows the refusal for a buy.

### 1. Token allowed

Reads the `allowed` flag in the token's `TokenConfig`, its [per-token settings](/docs/concepts/mandate#per-token-settings), which a `BUY` needs to be true. The `Mandate` struct itself names no tokens. A `SELL` needs only a market (`allowed` is true, or a feed or a pool is still set), so a stock the owner delisted can still be sold ([exit-only](/docs/help/glossary#exit-only)). A token that is not allowed and has no feed and no pool can be neither bought nor sold. See `test_tokenNotAllowed`, `test_exitOnlyTokenCanBeSoldNotBought` and `test_fullyDelistedTokenCannotBeSold`.

### 2. Token not paused

Asks the [B20](/docs/help/glossary#b20) token whether its transfers are paused. A paused token returns `TOKEN_PAUSED`, and so does a token whose `isPaused` call reverts. See `test_refusesPausedToken` and `test_revertingIsPausedFailsClosed`.

### 3. Transfer policy

A B20 token can name sender, receiver and executor policies, and the vault asks the policy registry whether each leg of the transfer path is authorized; a leg that is not authorized, or that cannot be read, returns `POLICY_BLOCKED`. For a `BUY` the legs are the pool as sender and as executor, the vault as receiver, and `tx.origin` as executor; for a `SELL` they are the vault and the swap adapter as senders, the adapter and the pool as receivers, and the adapter and `tx.origin` as executors. `tx.origin` is the account that signed the outer transaction, not the [executor](/docs/help/glossary#executor) address that `execute` checks. For an executor that is a plain account with no code, such as the agent's [CDP](/docs/help/glossary#cdp-server-wallet) account, the two are the same. If the executor has code, for example a multisig owner made executor for an unwind, the address checked is the EOA that submits the transaction, and behind a bundler it is the bundler's address. That account must pass the executor policy of the stock that the [intent](/docs/help/glossary#intent) trades or moves as collateral, and `previewIntent` must be called with `from` set to it, or the [preview](/docs/help/glossary#preview) can give another answer ([tx.origin in the policy check](/docs/security/not-claimed#txorigin-in-the-policy-check)). `SUPPLY` and `WITHDRAW_COLLATERAL` check `tx.origin` the same way. See `test_refusesWhenPolicyBlocksVault`, `test_policyOnSellChecksAdapterAndPool` and `test_revertingPolicyIdFailsClosed`.

### 4. Market open

Asks the calendar contract whether the market is open now, under the mandate's `sessionMode`. A closed market returns `MARKET_CLOSED`, and so does a calendar that reverts. [Market hours](/docs/concepts/market-hours) explains the two modes, daylight saving, holidays and early closes. See `test_refusalIsLoggedNotReverted`, `test_thanksgivingIsMarketClosedAtVaultLevel` and `test_revertingCalendarFailsClosed`.

### 5. Fresh oracle price

Reads the Chainlink answer for the stock. An answer that is zero or negative, has no timestamp, is dated in the future or cannot be read returns `BAD_PRICE`. A readable answer older than `maxStaleness` (default <Fact name="mandate.maxStalenessSec" />) returns `FEED_STALE`. [Prices and premium](/docs/concepts/prices-and-premium) has the details. See `test_refusesStaleFeed`, `test_feedStaleAndBad` and `test_readFeedRejectsBadAnswers`.

### 6. Stable multiplier

A B20 stock has a [uiMultiplier](/docs/help/glossary#uimultiplier) that changes on a split or a dividend. The vault returns `MULTIPLIER_COOLDOWN` when the multiplier differs from the vault's last snapshot, when it changed less than `multiplierCooldown` ago (default <Fact name="mandate.multiplierCooldownSec" />), when an update is scheduled but not yet in effect, or when it cannot be read. [Splits and the multiplier](/docs/concepts/splits-and-multiplier) covers the mechanism. See `test_multiplierChangeStartsCooldown`, `test_pendingMultiplierBlocks` and `test_revertingUiMultiplierFailsClosed`.

### 7. Pool price near the oracle

Reads the pool's [TWAP](/docs/help/glossary#twap) over `twapWindow` and compares it with the oracle price. A `twapWindow` of zero, a pool whose `observe` call reverts, or a TWAP that works out to a price of zero returns `BAD_PRICE`. An `observe` answer that is too short or does not decode, the pool's `token0()`, the stock's `decimals()` and the arithmetic that turns the answer into a price all fall outside the `catch`, so a revert in any of them reverts `execute` instead ([Fail closed](/docs/security/model#fail-closed)). A gap larger than `maxPremiumBps` (default <Fact name="mandate.maxPremiumBps" />), measured as a share of the oracle price, returns `PREMIUM_TOO_HIGH`. The gap counts in both directions: a pool price below the oracle is refused the same way as one above it. See `test_refusesPremium`, `test_premiumTooHigh` and `test_premiumBps`.

### Guard: balance and amount

Reads the vault's USDC balance for a `BUY` and its balance of the stock for a `SELL`. An amount of zero, or one above the balance, returns `INSUFFICIENT_BALANCE`. It runs after check 7 so that a market reason wins. See `test_insufficientBalance` and `test_marketReasonTakesPrecedenceOverBalance`.

### 8. Size limits

Takes the trade's notional in USDC: the amount for a `BUY`, the stock amount valued at the oracle price for a `SELL`. It returns `SIZE_LIMIT` when the notional is above the per-trade cap (default <Fact name="mandate.perTradeCapUsd" />), or when the day's counted volume plus the notional would go over the daily cap (default <Fact name="mandate.dailyCapUsd" />). Every allowed `BUY` (its USDC), `SELL` (its value at the oracle price) and `PAY_EXPENSE` adds to the counter `spentOnDay` for the UTC day, so a sale uses the daily cap like a purchase. Refused and failed actions add nothing, and neither do the credit actions. The day is a UTC day: `today()` is `block.timestamp / 1 days`, so the counter starts again at 00:00 UTC. See `test_perTradeCap`, `test_dailyCap`, `test_sellAfterBuy`, `test_payExpenseSharesDailyCapWithTrades` and `test_dailyCapResetsOnUtcDayRollover`.

### 9. Concentration

Applies to a `BUY` only. The vault adds up its net equity (USDC, every listed stock it holds and every stock supplied as collateral, minus any credit debt, so borrowing cannot loosen the cap) and returns `CONCENTRATION` when the bought stock's weight after the buy would be above its `maxWeightBps` (default <Fact name="mandate.maxWeightBps" />). A holding that is not allowed, or whose price is stale or unreadable, counts as zero. An unreadable position or debt amount, or debt at or above the assets, counts as a weight above any cap. See `test_concentration`, `test_concentrationNetsCreditDebt` and `test_unreadableCollateralFailsConcentrationClosed`; the last two are in [MandateVaultCredit.t.sol](https://github.com/duongnq2798/maat/blob/main/contracts/test/MandateVaultCredit.t.sol).

## After the checks pass

The vault swaps with a minimum output it computes itself from the oracle price and `maxSlippageBps` (default <Fact name="mandate.maxSlippageBps" />), whatever `minOut` the agent sent. The agent can ask for a higher minimum, never a lower one: the vault uses the larger of the two (`test_slippageFloorIsEnforcedEvenIfAgentSendsZero`, `test_agentMinOutAboveFloorIsUsed`). A swap or transfer that fails is recorded as `SWAP_FAILED` or `TRANSFER_FAILED`, and `execute` still does not revert (`test_swapRevertIsRecorded`).

## Other actions

`PAY_EXPENSE`, `SUPPLY`, `WITHDRAW_COLLATERAL`, `BORROW` and `REPAY` run their own subsets of these checks. The pause flag applies to all of them except `REPAY`.

| Action | What the vault checks | Works when the market is closed? | Works when the vault is paused? |
| --- | --- | --- | --- |
| `PAY_EXPENSE` | The payee is on the allowlist, the amount is non-zero and within the USDC balance, and it fits the per-trade and daily caps | Yes | No |
| `SUPPLY` | The token is allowed and the credit adapter supports it, the token is not paused, the transfer path passes the policy registry, and the amount is non-zero and within the stock balance | Yes | No |
| `WITHDRAW_COLLATERAL` | The token is listed and supported, not paused, and the path passes the policy registry; the amount is non-zero and within what is supplied. With debt outstanding it also needs an open market, and every supplied stock must be unpaused, with a valid, fresh feed answer and a stable multiplier; then the adapter checks the [health factor](/docs/help/glossary#health-factor) after the withdrawal | Yes with no debt, no with debt | No |
| `BORROW` | The token is USDC and the amount is non-zero; the market is open; every supplied stock is allowed, not paused, and has a valid, fresh feed answer and a stable multiplier; the projected health factor stays at or above the floor (the target inside the [de-risk window](/docs/help/glossary#de-risk-window)) | No | No |
| `REPAY` | The token is USDC, and the amount is non-zero and within the USDC balance | Yes | Yes |

Each row lists its checks in the order the vault runs them, and the first that fails names the reason. For the supplied stocks, the vault runs those checks one stock at a time, in the order the tokens were first listed, so the first stock that fails any of them names the reason. The pause flag runs before all of them, except for `REPAY`. When a credit view that a step needs cannot be read (the adapter's `supportsToken`, its collateral custodian or operator, `suppliedOf`, `debt` or the projected health factor), that step returns `CREDIT_FAILED`.

The four credit actions return `ACTION_NOT_SUPPORTED` when the mandate has no credit adapter, before any other check of their own. They are not limited by the per-trade or daily caps. A `BORROW`, and a `WITHDRAW_COLLATERAL` made while debt is open, must clear the health factor floor; `SUPPLY` and `REPAY` are limited only by what the vault holds. [Credit and the health factor](/docs/concepts/credit-and-health-factor) covers them.

## What the checks do not do

They do not judge whether a trade is a good idea. A trade inside every limit is allowed, even a bad one;
the limits bound how much a bad trade can cost. They also do not predict how the action will go: `previewIntent` returns the verdict of the checks, not the execution result, so it cannot see `SWAP_FAILED`, `TRANSFER_FAILED`, a `CREDIT_FAILED` from the credit call itself, or a `HEALTH_FACTOR_LOW` or `DERISK_WINDOW` from the credit adapter's own check. See [the threat model](/docs/security/threat-model).
