The agent takes all of its settings from environment variables. This page lists each one, says whether you must set it, gives its default, and says what it changes in the loop, so you can fill in a `.env` file without reading the code. The agent is built and fork-tested, and it has run in [live mode](/docs/help/glossary#live-mode) only on a fork. The fork run used a scripted proposer and a local sender, and the path through the [CDP Server Wallet](/docs/help/glossary#cdp-server-wallet) is tested against a fake client only. No output from the real Claude API is committed yet, and CDP has never been run for real.

<EnvTable />

`npm run agent` loads `agent/.env` when that file exists, and `agent/.env.example` is the template to copy. Git ignores `.env` files, so the file stays on your machine: keep every secret in it and never commit it. The agent checks its own settings once, at startup, in `agent/src/config.ts`. A blank value (`KEY=`) counts as unset, so a default applies, and a required setting that is blank is reported as missing. If any check fails, the agent stops before it does anything else, with one `invalid agent config` error that names each problem. It does not check the settings that the SDKs read, which is why the Required column says No for them.

`contracts/.env` is a different file. The commands you run in `contracts/` read it, and the agent does not. It repeats `BASE_RPC_URL`, `MAAT_EXECUTOR` and `MAAT_EXPENSE_PAYEE` with other rules. There, `BASE_RPC_URL` also serves the contract [fork tests](/docs/help/glossary#fork-test), which read [Base](/docs/help/glossary#base) at pinned past blocks and so need an archive node. The two addresses there are what the deploy writes into the [vault](/docs/help/glossary#vault). Here, [`BASE_RPC_URL`](#base_rpc_url) needs no archive node, `MAAT_EXECUTOR` must be the vault's current [executor](/docs/help/glossary#executor) and `MAAT_EXPENSE_PAYEE` an address on its [payee](/docs/help/glossary#payee) list. So check `MAAT_EXECUTOR` before you copy it across. In the deploy that [deployments/README.md](https://github.com/duongnq2798/maat/blob/main/deployments/README.md) describes, it starts as the [owner](/docs/help/glossary#owner)'s own wallet, and it becomes the CDP account once the owner hands the role over with `setExecutor`. [The whole path](/docs/guides/deploy-your-own-vault#the-whole-path) shows which value goes in which file.

## Read by the agent

These settings are read by `agent/src/config.ts`. `BASE_RPC_URL`, `MAAT_VAULT`, `MAAT_EXECUTOR` and `MAAT_EXPENSE_PAYEE` have no default and are required in every mode. The addresses may be written in any letter case, and the agent converts them to checksum form.

### BASE_RPC_URL

<EnvVar name="BASE_RPC_URL" />

The RPC endpoint for Base mainnet. It must be a valid URL. The agent builds one client on it, with `BASE_RPC_URL_FALLBACK` behind it when that is set, and uses that client for everything it reads: the vault state at a single block, the `previewIntent` calls, the gas estimates, the receipts, and the logs it uses to settle a transaction left pending by an earlier [round](/docs/help/glossary#round). It does not send transactions through this endpoint: in live mode the CDP wallet sends them. The agent does not need an archive node. A provider URL often contains a key, so treat it as a secret. The agent does not print it, and a round that halts on a failed read keeps only the first line of the error, redacted, which leaves the URL out of the journal.

### BASE_RPC_URL_FALLBACK

<EnvVar name="BASE_RPC_URL_FALLBACK" />

A second RPC endpoint for Base mainnet. It is optional, and when it is set it must be a valid URL. Every read still goes to `BASE_RPC_URL` first, and moves to this endpoint only when that request fails, for example on a timeout or a rate limit. Without it, a failed read makes the round do nothing or halt it. Take it from another provider, so that one outage does not stop both. It needs no archive node either, and the agent keeps it out of its output the same way as `BASE_RPC_URL`, so a URL with a key in it stays a secret.

### MAAT_VAULT

<EnvVar name="MAAT_VAULT" />

The address of the `MandateVault` the agent reads and sends to. For a vault you deploy, you get it from the deploy logs, and the address of Maat's own vault is on [Base addresses](/docs/reference/base-addresses). The agent's guarded sender sends only to this address and refuses any other target. The CDP policy that `cdp-setup.ts` attaches names one vault, so use the same address in both places. The zero address in `.env.example` is a placeholder, so replace it.

### MAAT_EXECUTOR

<EnvVar name="MAAT_EXECUTOR" />

The address of the [executor](/docs/help/glossary#executor), the one address the vault accepts `execute` from. The agent makes every [preview](/docs/help/glossary#preview) and every gas estimate as this address. In every round, in every mode, once it has read the vault it compares this address with the executor the vault reports. If they differ, the round ends with the status `wrong-executor` and an error line in the [journal](/docs/help/glossary#journal), and nothing else happens. In live mode it must also be the address of the CDP account named by `CDP_ACCOUNT_NAME`, and the agent stops at startup if it is not. The owner points the vault at the CDP account with `setExecutor`.

### MAAT_EXPENSE_PAYEE

<EnvVar name="MAAT_EXPENSE_PAYEE" />

The address the agent pays its [compute bill](/docs/help/glossary#compute-bill) to. It goes into the `payee` field of each `PAY_EXPENSE` [intent](/docs/help/glossary#intent). The vault pays only a [payee](/docs/help/glossary#payee) on its allowlist, so use an address on that list: a payee given to the deploy script (its own `MAAT_EXPENSE_PAYEE`, or its optional `MAAT_EXPENSE_PAYEE_2`), or one the owner added later through the [timelock](/docs/help/glossary#timelock). The agent pays only this address and does not read the vault's list, so with two payees allowlisted, this setting picks which one it pays.

For any other address the vault's preview returns [`PAYEE_NOT_ALLOWED`](/docs/concepts/refusal-codes#payee_not_allowed). The agent does not log that [reason](/docs/help/glossary#reason) onchain, so it never sends the payment and no [`Decision`](/docs/help/glossary#decision) appears. The bill stays unpaid. Once it reaches the bill minimum ([`MAAT_BILL_MIN_USD`](#maat_bill_min_usd)), each round that reaches the proposal step writes an `intent` line for it in the journal, with the preview `PAYEE_NOT_ALLOWED` and the gate `PAYEE_NOT_ALLOWED not worth a log tx`. While the vault is paused, the preview and the gate name `VAULT_PAUSED` instead, and when the vault holds no USDC the round writes a `skip` line for it. To clear it, fix this setting, or have the owner add the address through the timelock. The agent needs this setting even in [dry-run](/docs/help/glossary#dry-run) mode.

### MAAT_MODE

<EnvVar name="MAAT_MODE" />

The only values are `dry-run` and `live`, and anything else stops the start. The default is `dry-run`. In dry-run mode the agent reads the chain, asks Claude, previews every intent and writes its journal, but it never sends a transaction and it never connects to CDP. In live mode it also sends through the CDP wallet, which needs `MAAT_BUILDER_CODE` and the three CDP credentials. The flag `--dry-run` on the command line forces dry-run whatever this setting says. The flag is applied after the settings are checked, so `MAAT_MODE=live` without a [Builder Code](/docs/help/glossary#builder-code-erc-8021) still stops the start.

### MAAT_BUILDER_CODE

<EnvVar name="MAAT_BUILDER_CODE" />

A Builder Code that you registered for your project. Live mode requires it, and the Required column says so. Dry-run mode does not use it. In live mode the agent turns it into an ERC-8021 suffix and appends the suffix to the calldata of every transaction it sends. The code must match `^[a-z0-9_]{1,32}$`, and the agent checks that when it builds the runtime for live mode, before any CDP call. Transactions that the owner signs, such as the deploy, `fund` and `setExecutor`, do not carry it; the first-decision `BUY` intents of the go-live runbook, `deployments/go-live.md`, do, because the owner sends them with the calldata that `agent/scripts/first-decision.ts` builds. The owner registered Maat's own code, and the calldata of the vault's first `Decision` on Base mainnet carries it. [Run the agent](/docs/guides/run-the-agent#go-live) says where to register one.

### MAAT_LOOP_MODEL

<EnvVar name="MAAT_LOOP_MODEL" />

The model the agent asks for its proposals. The name goes to the Claude API as written, and the agent does not check it against a list. The request also turns on the API's server-side fallback (`fallbacks: "default"`), so the answer may come from another model. A `fallback` block in the response marks where one model's output gives way to the next, and the agent keeps only the text after the last one. Only a fake response has tested this. The agent books the cost of each answer at the price of the model that produced it. If the requested model declines and the API hands the request to a fallback model, the agent books the declined attempt and the fallback attempt each at its own model's price. It has prices for `claude-sonnet-5-5`, `claude-sonnet-5`, `claude-opus-5-5`, `claude-opus-5` and `claude-opus-4-8`, and it books any other name at the `claude-opus-4-8` rate, the highest in its table. A model that costs more than that is billed too low. Claude is called only at `https://api.anthropic.com`, whatever `ANTHROPIC_BASE_URL` says ([`ANTHROPIC_API_KEY`](#anthropic_api_key)). The journal's `run` line records the cost but not the model. That cost becomes the compute bill the agent pays, as [The treasury loop](/docs/concepts/treasury-loop#paying-its-own-bill) explains.

### MAAT_DATA_DIR

<EnvVar name="MAAT_DATA_DIR" />

The directory where the agent keeps its files. A relative path is relative to the directory you start the agent from, which is `agent/` when you use `npm run agent`, and the agent creates the directory when it is missing. It holds `state.json` (compute bills, dry-run rounds included, the amount paid, [refusals](/docs/help/glossary#refusal) logged per NYSE date, transactions sent per UTC day, and sends not yet settled), `journal.jsonl` (the append-only journal), `heartbeat.json` (when the last round ended) and `agent.lock`. The lock allows one agent per directory: a second agent stops at startup with an error that names the process holding the lock. Git ignores `agent/data/`.

A directory belongs to one mode. A dry-run round adds the cost of its Claude answer to the bill like any other round, so live mode refuses to start on a directory whose journal holds dry-run rows, and the vault never pays for the dry runs. A dry run refuses a directory whose journal holds live rows in the same way. Give each its own `MAAT_DATA_DIR` ([Switch to live mode and run one round](/docs/guides/run-the-agent#switch-to-live-mode-and-run-one-round)). The directory also belongs to one vault, and `state.json` does not record which. When you change `MAAT_VAULT`, start with a new `MAAT_DATA_DIR`. Otherwise the unpaid bill, the compute history that sets the [runway](/docs/help/glossary#runway), the refusals already logged, the day's transaction count and any pending send carry over to the new vault. A pending send whose transaction hash the agent recorded, and that succeeded on the old vault, is never seen as used on the new one, so every round then ends `pending-tx`. One with no recorded hash ends rounds `pending-tx` too, until it is dropped after at least <Fact name="pendingWindowMinutes" /> of chain time. No test covers a change of vault: this is what the code does.

### MAAT_MAX_TX_PER_DAY

<EnvVar name="MAAT_MAX_TX_PER_DAY" />

The most transactions the agent sends in one UTC day, by default <Fact name="maxTxPerDay" />. It must be a positive whole number. The count includes every `execute` and `syncMultiplier` the agent sends or tries to send, including refusal logs and bill payments, and it is kept in `state.json`, so a restart does not reset it. The agent checks the count before each send. When the cap is reached, the round stops with the status `halted` and a reason that begins `daily tx cap`. The cap exists so that a repeating error cannot burn gas all day. In dry-run mode the agent sends nothing, so the count stays at zero.

### MAAT_DEFAULT_DAILY_COMPUTE_USD

<EnvVar name="MAAT_DEFAULT_DAILY_COMPUTE_USD" />

The daily compute cost, in US dollars, that the agent assumes until it has a history of its own. The default is <Fact name="dailyComputeUsd" />, and it must be a positive number. The policy aims to keep <Fact name="runwayDays" /> of that cost as USDC, the [runway](/docs/help/glossary#runway). A `BUY` it suggests uses only the USDC above the runway and the unpaid bill. When USDC falls short of the runway plus the unpaid bill by at least <Fact name="minTradeUsd" />, it suggests a `BORROW`, but only if [`MAAT_CREDIT_ACTIONS`](#maat_credit_actions) is `on`, the vault is not paused, the credit position can be read and stock from the policy's [basket](/docs/concepts/treasury-loop#the-basket) with a valid [feed](/docs/help/glossary#chainlink-equity-feed) price is supplied as collateral. These are suggestions. Claude is told to adopt, resize or drop them, and the agent caps a proposed `BUY` at the vault's USDC balance, not at the runway. So the runway is a target, not a limit ([Runway and borrowing](/docs/concepts/treasury-loop#runway-and-borrowing)). The vault's per-trade and daily caps still bound every trade. As soon as one of the days before today, up to a week back, has a recorded cost, the agent uses the average of the recorded days instead of this setting.

### MAAT_CREDIT_ACTIONS

<EnvVar name="MAAT_CREDIT_ACTIONS" />

Whether the agent may use the vault's Aave credit line. The only values are `off` and `on`, and anything else stops the start. The default is `off`. While it is off, the policy suggests no `SUPPLY`, `WITHDRAW_COLLATERAL`, `BORROW` or `REPAY`, the system prompt tells Claude never to propose one, and a credit action that Claude proposes anyway is journaled as a `skip`, with an error that begins `credit actions are off`, before any preview or send. Buys, sells and bill payments are not affected. With `on`, the policy also supplies idle stock, borrows for the [runway](/docs/help/glossary#runway) and repays from new revenue ([The treasury loop](/docs/concepts/treasury-loop#runway-and-borrowing)), and the vault's own credit checks still bound each action. The startup line shows the setting as `credit=off` or `credit=on`.

### MAAT_MAX_LLM_USD_PER_DAY

<EnvVar name="MAAT_MAX_LLM_USD_PER_DAY" />

The most the agent spends on Claude in one UTC day, in US dollars, by default <Fact name="maxLlmUsdPerDay" />. It must be zero or a positive number. Before each Claude call the agent compares the day's recorded Claude cost with this cap, so the call that crosses it is the day's last. Once the cap is reached, the later rounds of that day do not call Claude: their `run` line has `ok` false and an error that begins `llm cap:`, and they still pay a compute bill that is due and send any `syncMultiplier` the vault needs. A cap of `0` keeps the agent from calling Claude at all. The cost is the agent's own estimate from its price table ([`MAAT_LOOP_MODEL`](#maat_loop_model)), and your Anthropic billing is the real figure.

### MAAT_BILL_MIN_USD

<EnvVar name="MAAT_BILL_MIN_USD" />

The smallest unpaid [compute bill](/docs/help/glossary#compute-bill), in US dollars, that a round pays with a `PAY_EXPENSE`. It is optional, and when it is set it must be a positive number. Unset, the minimum is <Fact name="liveBillMinUsd" /> in live mode and <Fact name="billMinUsd" /> in dry-run, where the bill payment only shows in the journal. A set value applies in both modes. A higher minimum means fewer, larger payments, each still bound by the vault's per-trade and daily caps. The startup line shows the minimum in force as `bill-min=`.

### CDP_ACCOUNT_NAME

<EnvVar name="CDP_ACCOUNT_NAME" />

The name of the CDP Server Wallet account that acts as the executor. `cdp-setup.ts` creates the account under this name or finds it, and the agent looks it up by name in live mode. The agent never creates an account. Dry-run mode does not use this setting.

## Read by the SDKs

`agent/src/config.ts` does not read these settings. The agent hands `ANTHROPIC_API_KEY` to the Anthropic SDK when it builds its Claude client, and the Coinbase CDP SDK reads its three from the environment when the agent first uses it. Because `agent/src/config.ts` does not check them, the agent does not check for them at startup, and the Required column says No. That No does not mean a run can do without them. Which run needs which one:

| Setting | Which run needs it |
| --- | --- |
| `ANTHROPIC_API_KEY` | Every run that reaches the Claude step, in dry-run and in live mode |
| `CDP_API_KEY_ID`, `CDP_API_KEY_SECRET`, `CDP_WALLET_SECRET` | Live mode only. `cdp-setup.ts` needs them too |

A missing credential is reported when the call that needs it is made: a CDP credential by the SDK, the Anthropic key by the agent. Keep the values in `.env`. Never paste one into an issue, a log or a chat.

### ANTHROPIC_API_KEY

<EnvVar name="ANTHROPIC_API_KEY" />

An API key from your own Anthropic account. The agent builds its Claude client the first time it asks for a proposal, and reads the key then. The client always calls `https://api.anthropic.com` with this key: it ignores `ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN`, so a proxy or a login token set for another tool cannot take the agent's requests, and the agent prints one warning at startup, `maat agent: ignoring ...`, when either is set. Every round that reaches the proposal step needs the key, in dry-run mode as well as in live mode, and Anthropic bills each request. A round that ends earlier does not use the key, for example one that ends with the status `no-state`, `wrong-executor` or `pending-tx`. Without a key the round's Claude step fails with `ANTHROPIC_API_KEY is not set`, and the agent records the failure in the round's `run` line in the journal, as `ok: false` with the error. That round then has no proposals from Claude. `smoke-claude.ts` needs the key as well.

### CDP_API_KEY_ID

<EnvVar name="CDP_API_KEY_ID" />

The ID of the API key you create in the Coinbase Developer Platform portal at [portal.cdp.coinbase.com](https://portal.cdp.coinbase.com). Live mode needs it, because the agent looks up the executor account through CDP before the first round. Dry-run mode does not use it.

### CDP_API_KEY_SECRET

<EnvVar name="CDP_API_KEY_SECRET" />

The secret that belongs to the API key above, from the same portal. Live mode and `cdp-setup.ts` are the only places in the repository that use it.

### CDP_WALLET_SECRET

<EnvVar name="CDP_WALLET_SECRET" />

The Wallet Secret that you create in the same portal. The agent needs it in live mode, where the CDP wallet signs and sends every transaction, and `cdp-setup.ts` reads it too. Dry-run mode does not use it.

## What each mode needs

A dry run that gets proposals from Claude needs the required settings and an Anthropic key. This is the smallest `.env` for it, with placeholders where your values go:

```text
BASE_RPC_URL=<BASE_RPC_URL>
MAAT_VAULT=<VAULT_ADDRESS>
MAAT_EXECUTOR=<EXECUTOR_ADDRESS>
MAAT_EXPENSE_PAYEE=<PAYEE_ADDRESS>
ANTHROPIC_API_KEY=<ANTHROPIC_API_KEY>
```

Live mode adds a mode, a Builder Code and the three CDP credentials. `CDP_ACCOUNT_NAME` is needed only if you named the account something other than the default.

```text
MAAT_MODE=live
MAAT_BUILDER_CODE=<BUILDER_CODE>
CDP_API_KEY_ID=<CDP_API_KEY_ID>
CDP_API_KEY_SECRET=<CDP_API_KEY_SECRET>
CDP_WALLET_SECRET=<CDP_WALLET_SECRET>
```

For the steps that produce these values, see [Run the agent](/docs/guides/run-the-agent).
