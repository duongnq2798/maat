This guide takes you from a clone of the repository to a `MandateVault` with the default [mandate](/docs/help/glossary#mandate) on Base mainnet: a dry run on a fork that needs no key, a checklist, the broadcast from your own wallet, funding, and a small smoke test. It is written for a builder who will own the vault. Every transaction is signed by you, from your own wallet, and no script in this repository holds a key.

<Callout type="fork" title="Not deployed yet">

The Maat team has not broadcast this deploy. The address table in `deployments/README.md` is empty today, and no page in these docs is labeled live. The deploy script is simulated on a fork by the contract test `test_deployWiresEverything`. The vault's `execute` runs on a fork in the contract fork tests and in the agent's fork test, and `fund` runs in the agent's fork test (the contract fork tests fund the vault with a cheat code instead). The commands below, including the broadcast, the verification and the smoke test, are copied from the runbook and have not been run by the Maat team, so they are not proven on mainnet. The contracts are unaudited.

</Callout>

## Before you start

You need the pieces below. Your wallet is the [owner](/docs/help/glossary#owner) of the vault, so the steps that sign are marked **Owner only**.

| Need | Detail |
| --- | --- |
| [Foundry](https://getfoundry.sh) | 1.8.4 or newer. It provides `forge script` and `cast`. |
| A Base mainnet RPC | Your own URL, written `<BASE_RPC_URL>` here, in `contracts/.env`. The dry run forks it. |
| A deployer wallet | A Foundry keystore account, named `maat-owner` in the runbook. It needs enough ETH on Base to pay gas for the deploy. |
| Four addresses, and an optional fifth | `MAAT_DEPLOYER`, `MAAT_OWNER`, `MAAT_EXECUTOR` and `MAAT_EXPENSE_PAYEE`, read by the deploy script, and an optional second payee, `MAAT_EXPENSE_PAYEE_2`. |
| An Etherscan v2 API key | `ETHERSCAN_API_KEY` in `contracts/.env`, for `--verify`. A v2 key works for Basescan. |
| USDC on Base | What you fund the vault with. |

`contracts/.env.example` lists `BASE_RPC_URL` and the five addresses, the optional one at the zero address; add `ETHERSCAN_API_KEY` yourself. Git ignores `contracts/.env`. The deploy script reads the addresses like this:

```solidity title="contracts/script/Deploy.s.sol#L23-L27"
        address deployer = vm.envAddress("MAAT_DEPLOYER");
        address owner = vm.envAddress("MAAT_OWNER");
        address executor = vm.envAddress("MAAT_EXECUTOR");
        address payee = vm.envAddress("MAAT_EXPENSE_PAYEE");
        address payee2 = optionalAddress("MAAT_EXPENSE_PAYEE_2"); // optional: unset or zero adds none
```

In the runbook the owner is your wallet, the [executor](/docs/help/glossary#executor) is temporarily your wallet until the [CDP Server Wallet](/docs/help/glossary#cdp-server-wallet) takes over, and the [payee](/docs/help/glossary#payee) is the compute-expense wallet, the address the vault's `PAY_EXPENSE` action may pay. Its `.env` step sets all three to your wallet address. The deploy uses [`MaatConfig.defaultMandate`](/docs/concepts/mandate#the-default-mandate) with the `REGULAR` session and the three-stock basket. To change a limit, a token or the payee, read [Configure a mandate](/docs/guides/configure-a-mandate) before you deploy.

`MAAT_EXPENSE_PAYEE_2` is optional. Set it when you already know a second address the vault should be able to pay, for example an agent's Bankr wallet: the deploy puts it on the list at once, while adding it later takes `queuePayee` and a wait of <Fact name="timelockHours" />. The agent pays one address only: its own [`MAAT_EXPENSE_PAYEE`](/docs/reference/agent-configuration#maat_expense_payee) setting, which it reads at startup and puts in the `payee` field of every `PAY_EXPENSE` intent. It never reads the vault's list, so with two payees on it you choose in the agent's settings which one it pays, and moving it to the other takes a restart, not a timelock.

Time: not measured. No mainnet deploy has been run, and the runbook gives no durations.

## Deploy and fund

<Steps>

<Step>

### Dry-run it on a fork

The dry run needs no key and sends nothing. Run it in `contracts/`. It uses placeholder addresses, for simulation only, and takes the RPC from `contracts/.env`.

```bash
set -a; source .env; set +a
MAAT_DEPLOYER=0x0000000000000000000000000000000000000004 \
MAAT_OWNER=0x0000000000000000000000000000000000000001 \
MAAT_EXECUTOR=0x0000000000000000000000000000000000000002 \
MAAT_EXPENSE_PAYEE=0x0000000000000000000000000000000000000003 \
forge script script/Deploy.s.sol --fork-url "$BASE_RPC_URL"
```

deployments/README.md prints no output for the dry run, so none is shown. It has worked when the script finishes without an error. The script ends by logging these lines:

```solidity title="contracts/script/Deploy.s.sol#L55-L64"
        // Check these before broadcasting: owner is immutable on the vault and the calendar.
        console2.log("deployer            ", deployer);
        console2.log("owner (immutable)   ", owner);
        console2.log("executor            ", executor);
        console2.log("expense payee       ", payee);
        console2.log("expense payee 2     ", payee2 == address(0) ? "none" : vm.toString(payee2));
        console2.log("MarketCalendar      ", address(calendar));
        console2.log("AerodromeSwapAdapter", address(swapAdapter));
        console2.log("AaveV4CreditAdapter ", address(creditAdapter));
        console2.log("MandateVault        ", address(vault));
```

The first four logged lines show the placeholders you passed, not real addresses. The `expense payee 2` line comes from your `.env`, and reads `none` when it is unset or zero. The contract addresses will be different on mainnet. The runbook says to read the total estimated gas at the end of the output when you decide how much ETH the deployer needs. Foundry writes the dry-run files under `contracts/broadcast/*/*/dry-run/`, which Git ignores.

</Step>

<Step>

### Check before you broadcast

Go through this list before step 5.

<Callout type="warning" title="The owner cannot be changed">

`MandateVault` and `MarketCalendar` set the owner once, and neither has a function that changes it. A mistyped `MAAT_OWNER` means permanent loss of control: you cannot withdraw funds or change the mandate. Check it character for character in the simulation in step 4, which uses your real `.env`. The dry run above prints placeholders and proves nothing about your owner.

</Callout>

- **Gas.** The deployer wallet has enough ETH on Base to deploy the calendar, the swap adapter, the credit adapter and the vault. Fund extra, because gas prices change.
- **The deployer.** `MAAT_DEPLOYER` is exactly the address of the `--account` wallet that you broadcast with. The next paragraph says why.
- **The other addresses.** `MAAT_EXECUTOR`, `MAAT_EXPENSE_PAYEE` and, if you set it, `MAAT_EXPENSE_PAYEE_2` are correct. They can be changed later: the executor at once with `setExecutor`, and a payee only through the [timelock](/docs/help/glossary#timelock), which is <Fact name="timelockHours" /> long.
- **Verification.** `--verify` needs `ETHERSCAN_API_KEY` in `contracts/.env`. If the deploy finishes but verification fails, do not redeploy. The resume command is in step 5.
- **Funding.** Fund the vault with `approve` and then `fund(amount)` (step 6), never with a plain USDC transfer.
- **Later changes.** After the deploy, every change to the configuration is queued with `queueMandate`, `queueTokenConfig` or `queuePayee`, which publishes all parameters in an event. You wait <Fact name="timelockHours" />, then apply it within <Fact name="gracePeriodDays" /> after that. Past that deadline the change expires (`ChangeExpired`) and must be queued again. See [The timelock](/docs/concepts/timelock-and-roles#the-timelock).

The credit adapter is bound to the vault's address, so the script precomputes that address from the deployer's nonce and expects the vault to be the fourth contract the deployer creates:

```solidity title="contracts/script/Deploy.s.sol#L33-L35"
        // The credit adapter is bound to the vault's address, so the vault must be the 4th contract created from
        // the deployer's current nonce. Send no other transaction from the deployer until this script finishes.
        address predictedVault = vm.computeCreateAddress(deployer, vm.getNonce(deployer) + 3);
```

If the wallet is wrong, or it sends another transaction between the simulation and the broadcast, the script can stop with `vault address mismatch` or a nonce error. `vault address mismatch` happens in the simulation, before any transaction is sent, so no gas is lost: simulate again. A nonce error during the broadcast can leave the calendar, the swap adapter and the credit adapter deployed but unused. In that case, redeploy from scratch.

</Step>

<Step>

### Import your wallet and fill `.env`

<Callout type="warning" title="Owner only">

The owner runs and signs the commands in this section of the runbook from their own wallet. `cast wallet import` adds your key to a Foundry keystore under the name `maat-owner`, which the later commands pass as `--account`. The commands are copied from deployments/README.md, and the Maat team has not run them.

```bash
cast wallet import maat-owner --interactive
cast wallet address --account maat-owner
```

</Callout>

The second command only prints the wallet's address. It signs nothing and sends nothing. Edit `contracts/.env`:

- Set `MAAT_DEPLOYER` to the address just printed.
- Set `MAAT_OWNER`, `MAAT_EXECUTOR` (temporarily your own wallet) and `MAAT_EXPENSE_PAYEE` all to your wallet address.
- Leave `MAAT_EXPENSE_PAYEE_2` at the zero address, unless you want a second payee.
- Add `ETHERSCAN_API_KEY`.

</Step>

<Step>

### Simulate again with your real `.env`

This run uses no environment overrides, no `--broadcast` and no key. It is the check that the checklist points to.

```bash
set -a; source .env; set +a
forge script script/Deploy.s.sol --rpc-url "$BASE_RPC_URL"
```

Read the output yourself. It has worked only when both conditions hold:

- The `deployer`, `owner (immutable)`, `executor` and `expense payee` lines match your wallet address character for character, and `expense payee 2` reads `none` or the second payee you set.
- The simulation finishes, with no `vault address mismatch`.

If the simulation stops at `vault address mismatch` or a nonce error, fix the cause (use the right wallet, send no other transaction from the deployer wallet) and simulate again. No transaction has been sent at this step. deployments/README.md prints no output for this command, so none is shown.

</Step>

<Step>

### Broadcast

Broadcast only when both conditions above hold.

<Callout type="warning" title="Owner only">

This signs and sends the deploy transactions from your wallet and costs gas. The deploy cannot be undone, and the owner is permanent.

```bash
set -a; source .env; set +a
forge script script/Deploy.s.sol --rpc-url "$BASE_RPC_URL" --account maat-owner --broadcast --verify
```

If the deploy finishes but verification fails, do not redeploy. Run this instead:

```bash
forge script script/Deploy.s.sol --rpc-url "$BASE_RPC_URL" --account maat-owner --resume --verify
```

</Callout>

deployments/README.md prints no output for the broadcast, so none is shown. The script's last lines give the address of each contract, and Foundry records the transactions in `contracts/broadcast/Deploy.s.sol/8453/run-*.json` (step 8). Keep the vault address for the next steps.

</Step>

<Step>

### Fund the vault

Approve the vault to pull USDC, then call `fund`. Do not transfer USDC straight into the vault. `fund` pulls the USDC from the owner and records it, so it does not count as revenue. A direct transfer is not recorded until `notifyRevenue` runs. Anyone can call it, and `execute` calls it first once an intent has passed its checks. It then emits `RevenueReceived` for the difference. The agent reads the same gap between the vault's USDC balance and `recordedUsdc` as new revenue, and its policy answers new revenue by suggesting a repayment when the vault has debt and the amount to repay is at least the minimum trade size, <Fact name="minTradeUsd" />.

<Callout type="warning" title="Owner only">

These two transactions are signed by your wallet. The amounts are in USDC units, which have <Fact name="usdcDecimals" />. The runbook funds the vault with a small test amount, shown in the commands below in USDC units, and you can fund any amount you choose. Replace `<VAULT_ADDRESS>` with the vault address from the previous step. The USDC address is the one in [Base addresses](/docs/reference/base-addresses).

```bash
VAULT=<VAULT_ADDRESS>   # address of the MandateVault just deployed
USDC=0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913
cast send "$USDC" "approve(address,uint256)" "$VAULT" 20000000 --rpc-url "$BASE_RPC_URL" --account maat-owner
cast send "$VAULT" "fund(uint256)" 20000000 --rpc-url "$BASE_RPC_URL" --account maat-owner
```

</Callout>

deployments/README.md prints no output for these commands, so none is shown. The `fund` transaction emits a `Funded` event with the amount, and no `RevenueReceived`.

</Step>

<Step>

### Run the smoke test

Send one small BUY of NVDAc, then one on a weekend. Do the first only during US market hours, which the calendar sets at <Fact name="nyseOpen" /> to <Fact name="nyseClose" />, on a day that is not a market holiday. New York is <Fact name="etOffsetHours.dst" /> behind UTC during US daylight saving time and <Fact name="etOffsetHours.standard" /> behind otherwise. On an early-close day the session ends earlier, and an `execute` outside it is refused with `MARKET_CLOSED`.

The owner's wallet is the executor at this stage, so it can send `execute` itself. Run the smoke test before you hand the executor role to the CDP Server Wallet, because after the handover the owner's own `execute` calls revert with `NotExecutor`. The BUY amount in the commands is in USDC units too.

<Callout type="warning" title="Owner only">

The `execute` transaction is signed by your wallet. The `cast call` line only reads. Use the shell from the funding step, which set `VAULT`.

```bash
cast call "$VAULT" "previewIntent((bytes32,uint8,address,uint256,uint256,address,bytes32))(uint8)" "($(cast keccak maat-smoke-1),0,0xb20000000000000000000078ee7ce2fE4908108C,5000000,0,0x0000000000000000000000000000000000000000,$(cast keccak smoke))" --rpc-url "$BASE_RPC_URL"
cast send "$VAULT" "execute((bytes32,uint8,address,uint256,uint256,address,bytes32))" "($(cast keccak maat-smoke-1),0,0xb20000000000000000000078ee7ce2fE4908108C,5000000,0,0x0000000000000000000000000000000000000000,$(cast keccak smoke))" --rpc-url "$BASE_RPC_URL" --account maat-owner
```

For the weekend intent below, run both lines again with `maat-smoke-2` in place of `maat-smoke-1`. That second `cast send` is signed by your wallet too.

</Callout>

The intent has action `0`, which is `BUY`, and the token is NVDAc. The expected result, from deployments/README.md:

- The [preview](/docs/help/glossary#preview) from `previewIntent` returns `0`, which is `OK`.
- The `execute` transaction has a [`Decision`](/docs/help/glossary#decision) log with `allowed=true`.

Then send one more new intent, with the id `maat-smoke-2`, on a weekend, using the two commands in the callout. The `Decision` log must show `reason=6`, which is `MARKET_CLOSED`. Every intent id works once, so a repeat of `maat-smoke-1` would revert.

<Callout type="note" title="Preview from the executor">

The transfer-policy check ([check 3](/docs/concepts/nine-checks#3-transfer-policy)) reads `tx.origin`, which in a `cast call` is the `--from` address, or whatever address the node uses when none is given. For a BUY or a SELL, `previewIntent` therefore matches `execute` only if that address passes the stock's executor policy, as the executor's address does. The runbook's `cast call` sets no sender. If it returns `5`, which is `POLICY_BLOCKED`, repeat it with `--from <EXECUTOR_ADDRESS>`: your wallet is the executor at this stage.

</Callout>

</Step>

<Step>

### Record the addresses

deployments/README.md has a table with one row per contract: `MarketCalendar`, `AerodromeSwapAdapter`, `AaveV4CreditAdapter` and `MandateVault`. Its columns are the network, the contract, the address, the transaction and the date. Fill in the addresses and the transaction hashes from the broadcast and the smoke test. The addresses are in the script output. The transactions are in `contracts/broadcast/Deploy.s.sol/8453/run-*.json`, which holds the transactions and the deployer address but no key. Whether to commit that file is the owner's decision.

The Maat team's table is empty because nothing has been broadcast. If you deploy from your own copy of the repository, fill in your copy of the table, and keep the vault address for the agent's `MAAT_VAULT` setting.

</Step>

</Steps>

## Check it worked

- The simulation with your real `.env` printed your own address on the `owner (immutable)`, `executor` and `expense payee` lines, and no `vault address mismatch`.
- After the broadcast, a read-only call returns your addresses from the vault: `cast call "$VAULT" "owner()(address)" --rpc-url "$BASE_RPC_URL"` prints the owner, `cast call "$VAULT" "executor()(address)" --rpc-url "$BASE_RPC_URL"` prints the executor, and `cast call "$VAULT" "payees()(address[])" --rpc-url "$BASE_RPC_URL"` prints the payee list, with one address or two.
- `previewIntent` returned `0`, and the allowed BUY emitted a `Decision` with `allowed=true`.
- The weekend intent emitted a `Decision` with `reason=6`, `MARKET_CLOSED`, and `allowed=false`. A refusal moves no funds.
- The table in deployments/README.md has your four addresses.

## Common mistakes

- **A mistyped owner.** The owner is immutable on the vault and the calendar. Check the owner line of the simulation with your real `.env`, not the dry run.
- **A deployer that does not match the account.** `MAAT_DEPLOYER` must be the address of the `--account` wallet, and that wallet must send no other transaction between the simulation and the broadcast.
- **A plain USDC transfer instead of `fund`.** It is counted as revenue the next time `notifyRevenue` runs. Approve, then `fund`.
- **A smoke test out of session.** A BUY on a weekend or a holiday, or after the close, is refused with `MARKET_CLOSED` instead of returning `OK`. That is the vault working, but it is not the first smoke test. The refused intent still uses its id, so retry with a new one, such as `maat-smoke-3`.
- **A second payee equal to the first.** The script stops with `MAAT_EXPENSE_PAYEE_2 equals MAAT_EXPENSE_PAYEE` in the simulation, before anything is sent. For one payee, leave `MAAT_EXPENSE_PAYEE_2` at the zero address.
- **Redeploying because verification failed.** Run the resume command instead.
- **Handing the executor role over too early.** After `setExecutor` points at the CDP Server Wallet, your wallet's `execute` calls revert with `NotExecutor`.
- **Treating the dry-run addresses as yours.** The contract addresses in the dry run differ from mainnet, and the four address lines are placeholders.
