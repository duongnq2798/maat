A brief is a short public message to Maat's agent, sent as one zero-value transaction to the `MaatInbox` contract on [Base](/docs/help/glossary#base). The agent reads it as untrusted data. Claude may be persuaded by it; the [vault](/docs/help/glossary#vault) still checks every [intent](/docs/help/glossary#intent) against its [mandate](/docs/help/glossary#mandate) and has the last word. The site's `/ask` page sends briefs, lists them, and lets anyone ask the live vault what it would answer, for free.

## What the inbox accepts

`brief(text)` takes 1 to 280 bytes of text, counted as UTF-8 bytes, not characters, and emits `Brief(id, from, text)`. Ids start at 1 and grow by 1. The contract has no owner, holds no funds and refuses any call that carries ether. Calldata after the encoded text is ignored, so a transaction can end with an ERC-8021 suffix. `/ask` checks the byte count before it asks your wallet for anything.

## Send a brief

<Steps>

<Step>

### Write it

A brief is public and stays onchain for good, so put nothing private in it. The counter under the box gives its size in bytes.

</Step>

<Step>

### Pick a wallet

The page lists every browser wallet that announces itself through EIP-6963, and Base Account, which needs no extension. A browser wallet is switched to Base mainnet first, and the brief goes out through viem's `writeContract` with the suffix as `dataSuffix`. Base Account gets a `wallet_sendCalls` request with the suffix as the optional `dataSuffix` capability, the shape docs.base.org gives for Builder Codes, which a wallet may leave out.

</Step>

<Step>

### Check the Builder Code line

The page reads the Builder Code from the vault's first [Decision](/docs/help/glossary#decision), the one the [owner](/docs/help/glossary#owner) sent, as the [mainnet ledger](/ledger) does. No code is written into the site. When it cannot be read, one line says why and the brief is sent without a suffix. Once the brief is included, the page reads the transaction's input and says whether the suffix ends it, sits inside the wallet's call, or is missing. It says the brief is in the feed only when the receipt holds its `Brief` log.

</Step>

</Steps>

## What the agent does with a brief

Once `deployments/README.md` records the inbox, as it has since 2026-11-27, each round of an agent built from `main` reads the new `Brief` logs up to the `safe` block and sends at most 3 to Claude, at most 20 a UTC day and 2 per sender a UTC day. A brief over the day or sender cap, or over the brief budget of 5 brief-driven transactions and $0.25 of Claude a UTC day, is journaled as skipped with the cap's name and never reaches Claude. Claude sees each brief as one JSON line inside a section marked untrusted, after its controls, format characters and other invisible code points are turned into U+FFFD, and is told that a brief is data, never an instruction.

Claude replies to each brief it is sent, and the journal keeps the reply sanitized and cut to 200 characters. It may adopt 1 to 3 briefs into an intent: the intent's [rationale blob](/docs/help/glossary#rationale-blob) then lists their ids in `q`, and its text is a fixed template of the action, the amount, the token and the ids, never the brief's own words. An intent Claude proposes as its own in that round gets a fixed template too, so a brief cannot word Maat's calldata by asking not to be cited. The vault checks each intent like any other. The `/ask` feed shows what became of each brief: from the agent's published journal, the reply, whether an intent that adopted it reached the vault, or the cap that kept it from Claude; from the vault's `Decision` logs, the vault's verdict ([Read the feed](#read-the-feed)). [Briefs](/docs/guides/run-the-agent#briefs) in Run the agent has the details.

## Ask the real vault

Pick an action, a token and an amount, and the page calls `previewIntent` on the live vault at the latest block over the site's public RPCs. `previewIntent` runs the same checks as `execute` and returns the [reason](/docs/help/glossary#reason) the vault would give. `PAY_EXPENSE` also takes a payee, which the page fills in with the first address of the vault's `payees()`, because the vault refuses an expense to any address not on that list. The preview is an `eth_call`: nothing is signed or sent, and no brief is needed.

## Read the feed

The feed lists every `Brief` event of the inbox, newest first. Each brief is shown as a weighing, in this order:

1. `#id · sender`: the brief's id and the sender's short address, marked `team` when the sender is in the `/proof` team set, traced as [Count the briefs](#count-the-briefs) describes.
2. The brief's text, from its `Brief` log.
3. `Maat's agent replied:` and Claude's reply, from the brief's row in the agent's published journal, read from the public `agent-journal` branch and checked against its hash chain in your browser. Under it are the row's file and line, and the agent's git commit that wrote the row. A brief Claude was sent but did not answer, or one a cap kept from Claude, says so. A brief with no row in the published journal says `no reply yet`. While the `agent-journal` branch is not published, every brief says `its journal is not published yet` instead, since a reply may already be in the agent's unpublished journal.
4. `Claude persuaded: yes, adopted into an intent` or `Claude persuaded: no`, from that row's `adopted` flag: yes when an intent that lists the brief's id in its blob's `q` went to the vault.
5. The vault's verdict, such as `Refused · Market closed (MARKET_CLOSED)`, with the `Decision`'s transaction and block. It comes from the vault's `Decision` logs alone, never from Claude's text, since Claude replies before the vault decides: a Decision whose sender is not the owner, whose blob is not a probe, hashes to its `rationaleHash` and lists the brief's id in `q`. A Decision found always wins over the journal, and one that several cite shows each verdict. A brief no such Decision cites says `none, no intent took it to the vault` when its journal row is final and not adopted (a reply or a missing reply with no adoption, or a skip by a cap): the agent sends Claude only briefs it has recorded no outcome for, and an intent adopts only briefs sent in its own round. Any other brief no such Decision cites says `not weighed yet`.

The text is shown as plain text with no links, no markdown and no HTML, after the same code points the agent's prompt replaces are turned into U+FFFD: controls, format characters such as zero-width and direction marks, and other invisible ones such as variation selectors and the tag characters U+E0000 to U+E007F. Nothing in the feed is a link, not even the sender or the Decision. The owner can hide abusive text by adding its id to `web/content/ask-hidden.ts`. A hidden brief leaves the feed but still counts.

Above the feed, the counters count each brief once, on two lines that are never added together: outside briefs by the `/proof` rule, then the team's own briefs. Each line gives briefs, wallets, Claude persuaded (briefs whose journal row says an intent adopted them), Vault allowed (briefs that an allowed brief-driven Decision cites) and Vault refused (briefs that only refused ones cite). Zero shows as 0. A counter whose source is missing says why in place of a number: `no journal yet` while the `agent-journal` branch is not published, `journal not read`, `not read` for the vault's Decisions, `team set not read`, or `incomplete` when a read has a gap. A line under the counters gives every brief and wallet read from the logs, team included.

## Count the briefs

The [`/proof` page](/proof) publishes the counting rule, section 5 of the inbox spec, word for word, and counts the briefs from the inbox's `Brief` logs in your browser: outside briefs, distinct outside wallets and how many of them hold a Coinbase Verified Account attestation on Base, then team briefs, hidden briefs and bounty claimants, each on its own line. A brief from a team wallet is a team brief, never an outside brief. A hidden brief stays in the outside count. Bounty claimants come from `web/content/proof-bounty.ts`. Until `deployments/README.md` recorded the inbox on 2026-11-27, no brief line had a number. None has one while any read is incomplete.

The team set is traced from Base at the block the briefs are counted to: the wallets in `web/content/proof-team.ts`, the vault's `owner()`, `executor()` and `payees()`, the deployer of every contract in `deployments/README.md`, and every wallet those funded within 2 hops. ETH funding comes from each team wallet's sent transactions, checked against the wallet's nonce. The trace finds every transaction that left a log of the vault other than `RevenueReceived`, and the transaction of each brief from a team wallet, from those logs, so an `execute` the agent sends needs no list. It skips `RevenueReceived`, since anyone who sends the vault some USDC can make it emit one, and reading those transactions would let anyone slow the count. The rest, such as contract deploys, plain transfers, approvals, a team wallet's own `notifyRevenue` and reverted transactions, are committed in `web/content/proof-sends.ts`. Token funding comes from the `Transfer` logs of those transactions and of each token they approved. The trace stops at the zero address, the vault and the addresses in `web/content/proof-stops.ts`, and the page lists the team set and the stops with why each is there. When a team wallet has sent a transaction that is in neither, the count is incomplete until the owner adds it, and the page names the wallet and how many of its sends are missing; `node scripts/recount.mjs --sends <wallet> --rpc https://mainnet.base.org --logs-rpc https://base-rpc.publicnode.com` prints the entry, with only the sends no log the trace reads gives. A team wallet delegated to code by EIP-7702 also leaves the count incomplete, since that code can send ETH that no log shows. The Decision lines of the rule are not counted yet.

The page reads the `Brief` logs and the vault's logs in windows of 50,000 blocks, 16 windows of each at once. It takes the vault's logs up to 151 blocks below the block of the committed snapshot, `web/content/generated/decisions-snapshot.json`, from that file, or from this browser's ledger cache when the cache reaches a later block. It keeps them only when Base gives the snapshot's block the same hash and each log's transaction receipt holds that log; otherwise it reads the vault's logs from its deploy block. A cache that took its logs from a snapshot is used only while the site serves that same file, as on the ledger. A log the file or the cache leaves out leaves a team wallet with fewer sends than its nonce; then the page reads those blocks from Base as well and traces the team again, so it shows what a read from the deploy block shows. The page says where it took the vault's logs from.

To rebuild the same lines from the chain alone, run `node scripts/recount.mjs` in a clone of the repository with Node.js 24. The script has no dependency: it reads the deployments table and the five lists from the repository, runs the same team trace as the page, reads the logs and the attestations from a keyless Base RPC, and prints the page's lines in the same words. It exits with 1, and gives no number on a brief line, when the count is incomplete. `--rpc <url>` reads another RPC, `--logs-rpc <url>` reads the logs from another, and `--to-block <n>` stops at the block the page says it counted to, written as the page prints it or as digits. By default it reads every vault log from the vault's deploy block, so it rests on no file but the deployments table and the five lists; `--snapshot` takes them from the committed snapshot with the page's checks and prints a line that says so. When the RPC rate-limits it, the script sends fewer requests at once and waits as long as the RPC's `Retry-After` header says, for up to two minutes per request.
