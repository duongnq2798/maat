This page lists the rules the vault enforces, the code that enforces each one and a test that shows it, so you can check the claim "the agent proposes, the contract decides" against the code and not only against the README. Everything here is built and fork-tested. Nothing is deployed, the contracts are unaudited ([What Maat does not claim](/docs/security/not-claimed) says so first), and the real Claude API and the real CDP wallet have never run, so the agent-side rows describe code that was tested against fakes.

## The principle: the agent proposes, the contract decides

Claude reads the vault's state and proposes trades as JSON. The agent turns each proposal into an [intent](/docs/help/glossary#intent), and an intent can move money in only one way: it is sent to `execute` on the vault, which only the [executor](/docs/help/glossary#executor) may call. The vault then runs its checks, in its own code, against its own state. Every step before that (Claude, the agent's validation, the [preview](/docs/help/glossary#preview), the guarded sender and the CDP policy) is untrusted. Those steps save gas and keep a journal. They are not what makes a trade safe.

<Architecture />

This holds because of the following facts about the code, and the rest of the page shows where each one lives.

1. **Claude only produces data.** It holds no wallet key and calls no contract. The agent checks its answer against a schema and builds the intent itself.
2. **The executor can call `execute` and nothing else with any power.** Every other function is either open to anyone and harmless, or owner-only and reverts for the executor.
3. **`execute` decides in the contract.** The verdict depends on the intent and on the chain's state, and on nothing the agent says about them.
4. **What `execute` writes only records or tightens.** The bookkeeping it changes is the used-intent flag, the spent-today counter, the multiplier snapshot and the revenue record. No call from the executor loosens a rule, because a rule change needs the [owner](/docs/help/glossary#owner) and the [timelock](/docs/help/glossary#timelock).

This is the whole entry point, and it is short enough to read:

```solidity title="contracts/src/MandateVault.sol#L102-L113"
    function execute(Intent calldata intent) external returns (bool allowed, Reason reason) {
        if (msg.sender != executor) revert NotExecutor();
        if (usedIntent[intent.id]) revert IntentAlreadyUsed(intent.id);
        usedIntent[intent.id] = true;
        if (_hasMarket(tokenConfig[intent.token])) _syncMultiplier(intent.token);

        uint256 price;
        (reason, price) = _check(intent);
        if (reason == Reason.OK) reason = _perform(intent, price);
        allowed = reason == Reason.OK;
        emit Decision(intent.id, intent.action, intent.token, intent.amount, allowed, reason, intent.rationaleHash);
    }
```

A call from any other address reverts. A reused intent id reverts. The id is marked used before anything is checked, so a refused intent cannot be sent again either. Then the vault checks, acts only if the verdict is `OK`, and emits a `Decision` either way.

`_check` runs the <Fact name="checksPerTrade" /> checks for a `BUY` or a `SELL`, with check 9 (concentration) for a `BUY` only. The other actions run their own checks, such as the [payee](/docs/help/glossary#payee) allowlist for `PAY_EXPENSE` and the [health factor](/docs/help/glossary#health-factor) for `BORROW`. [The nine checks](/docs/concepts/nine-checks#other-actions) lists them.

## What the agent adds

The rows below are in the agent, which is TypeScript. They are not the security boundary. Anyone who holds the executor key can send to the vault without the agent, and the vault does not know the agent exists. These layers matter for a different reason: they stop a bug, a confused Claude or a failed network call from wasting gas, paying a bill twice or sending something nobody meant to send, and they keep the journal. The send path ran on a fork with a local sender. The CDP code was tested against a fake CDP client only.

The guarded sender and the CDP policy are the two layers that sit closest to the key, so here they are:

```typescript title="agent/src/exec/sender.ts#L39-L52"
  async send(tx: TxRequest): Promise<Hex> {
    if (getAddress(tx.to) !== getAddress(this.opts.vault)) throw new SendRefused(`target ${tx.to} is not the vault`);
    let fn: string;
    try {
      fn = decodeFunctionData({ abi: mandateVaultAbi, data: tx.data }).functionName;
    } catch {
      throw new SendRefused("calldata does not decode against the MandateVault ABI");
    }
    if (!(ALLOWED_FUNCTIONS as readonly string[]).includes(fn)) throw new SendRefused(`function ${fn} is not allowed`);
    if (typeof tx.gas !== "bigint") throw new SendRefused("gas limit is missing");
    if (tx.gas <= 0n) throw new SendRefused(`gas limit ${tx.gas} is not positive`);
    if (tx.gas > MAX_GAS) throw new SendRefused(`gas limit ${tx.gas} is above the cap ${MAX_GAS}`);
    return this.inner.send({ ...tx, data: withSuffix(tx.data, this.opts.suffix) });
  }
```

The two layers cover different things. The policy limits where a transaction may go, on which network and with how much value. It does not limit which function is called. The function limit is in the guarded sender, and the guarded sender runs inside the agent process. So the policy and the sender do not add up to a function allowlist for someone who holds the CDP credentials: they could ask CDP to send any calldata to the vault. That is acceptable only because the vault decides. Every function other than `execute` is open to anyone and harmless, or owner-only and reverts for the executor.

<Callout type="warning" title="Never run against the real CDP">

The CDP policy is tested for its shape only. [`cdpPolicy.test.ts`](https://github.com/duongnq2798/maat/blob/main/agent/test/cdpPolicy.test.ts) checks the rules the code builds, and no test shows that CDP enforces them, because the CDP code has never run against the real service. Treat the policy as one more layer that is untested where it counts, not as a guarantee.

</Callout>

## Refuse, do not revert

A reverted call leaves no record. A refusal does: `execute` returns `(allowed, reason)` and emits a `Decision` with the typed [reason](/docs/help/glossary#reason), so every refused `execute` call can be read later. A call that fails after the checks pass is caught too: a swap is recorded as `SWAP_FAILED` ([`test_swapRevertIsRecorded`](https://github.com/duongnq2798/maat/blob/main/contracts/test/MandateVault.t.sol)), a token transfer as `TRANSFER_FAILED` ([`test_payExpenseTransferRevertIsLogged`](https://github.com/duongnq2798/maat/blob/main/contracts/test/MandateVault.t.sol)) and a credit call as `CREDIT_FAILED` ([`test_adapterRevertNeverRevertsExecute`](https://github.com/duongnq2798/maat/blob/main/contracts/test/MandateVaultCredit.t.sol)). The refusal test shows the whole path on a Saturday:

```solidity title="contracts/test/MandateVault.t.sol#L30-L41"
    function test_refusalIsLoggedNotReverted() public {
        vm.warp(SAT_1800_UTC);
        feed.set(200e8, block.timestamp);
        Intent memory i = _intent(Action.BUY, 20e6);
        vm.expectEmit(true, true, false, true, address(vault));
        emit Decision(i.id, Action.BUY, address(nvda), 20e6, false, Reason.MARKET_CLOSED, i.rationaleHash);
        (bool allowed, Reason r) = _exec(i);
        assertFalse(allowed);
        _assertReason(r, Reason.MARKET_CLOSED);
        assertEq(usdc.balanceOf(address(vault)), 200e6);
        assertTrue(vault.usedIntent(i.id));
    }
```

The rule has limits:

- **A record exists only if someone sends the call.** The agent previews every intent first and sends a refusal onchain only when it is worth recording and its reason has not been logged for that NYSE date (for `MARKET_CLOSED`, for that closed phase). Other refusals are in the agent's journal only, so a missing `Decision` is not proof that the agent did not try.
- **"By design" is not "never".** Only `NotExecutor` and `IntentAlreadyUsed` are meant to revert. The README adds that plain ERC-20 `balanceOf` and `decimals` reads on USDC and the stocks are assumed not to revert, and no test makes one revert.
- **A refusal does not undo what the call already wrote.** It moves no money because the vault stops before it acts, but the intent id is spent, and a multiplier change that the call noticed on the way is recorded.

## Fail closed

The vault reads a lot of state it does not control: the token's pause flag and transfer policy, the calendar, the multiplier, the feed, the pool and the Aave position. When one of those reads reverts or cannot be understood, the vault takes the unsafe answer, refuses and records the refusal. It does not guess and it does not let the revert escape. This is the term [fail closed](/docs/help/glossary#fail-closed) in the glossary.

Some failures are not covered by fail closed, and the code says so:

- **An address with no code.** Solidity's `try`/`catch` does not catch a call to an address that has no contract. `GuardLib` says this in its comments, so the vault requires code at the calendar, the swap adapter, the credit adapter, each token, each feed and each pool when they are configured, and rejects the configuration with `InvalidConfig` otherwise. That check runs when a configuration is applied, never inside `execute`. The policy registry address is the exception: the constructor rejects only the zero address for it, and does not check it for code.
- **A dependency that lies.** Fail closed handles a read that reverts. It cannot handle a read that returns a wrong answer, such as a fresh but wrong price. That is a [trust boundary](#trust-boundaries), not a guard.

## Trust boundaries

The vault is built so that most parties do not have to be trusted. These are the ones it does rely on, and the ones it assumes can fail or lie.

**Trusted.** The vault has no independent check on these, or only a partial one.

| Party | What the vault relies on it for | If it fails |
| --- | --- | --- |
| **The owner key** | Pausing, replacing the executor, withdrawing and approving every rule change. There is one key, it is immutable and it has no transfer function | A leaked owner key is a loss of what the vault holds. See [the owner key](/docs/security/threat-model#the-owner-key) |
| **The contracts** | The vault, the calendar and the two adapters are the rules | They are unaudited. A bug in them is not caught by anything else |
| **Base** | The chain and its clock: [staleness](/docs/help/glossary#staleness), the session, the timelock and the daily cap all use `block.timestamp` | A chain halt or a reorg is outside what the vault can detect |
| **Chainlink** | A fresh, positive answer is taken as the price of one raw token. The pool is compared with it, never the other way round | An oracle that disagrees with the pool by more than the [premium](/docs/help/glossary#premium) limit is refused. An error inside that band is not caught |
| **The B20 precompiles** | The token's pause flag, its transfer policies, its `uiMultiplier` and the policy registry | The vault fails closed when a read reverts, not when a read lies |

Maat also calls the Aerodrome pools, [Aave V4](/docs/help/glossary#aave-v4) and USDC. It bounds what it sends to them (the swap floor, the size caps for trades, the health factor for a borrow and for a collateral withdrawal against debt, a payee allowlist) and does not audit their code. Credit actions are not limited by the trade caps: `SUPPLY` and `REPAY` have no size limit other than what the vault holds.

**Untrusted.** The vault assumes each of these can be wrong or hostile.

| Party | Why it is not trusted | What bounds it |
| --- | --- | --- |
| **Claude** | It can be wrong, or manipulated through the text it reads | The schema and the clamps in the agent, then the vault's checks and caps. A bad trade inside every limit is still allowed |
| **The agent process** | It can have a bug, or be taken over | The vault re-runs every check on every call, whatever the agent did before |
| **The executor key** | It lives on a server, in the CDP wallet, and can leak | It can call `execute` and nothing else with any power, and the owner can replace it at once |
| **The RPC** | A node can lie, lag or go down | The vault does not use it: the verdict is computed in the transaction against the chain's own state. A bad RPC can mislead only the agent's reads and bookkeeping |

[The threat model](/docs/security/threat-model) takes each of these through a leaked key and the other ways it can go wrong, and [How it is tested](/docs/security/testing) shows which of the claims above have a test and which do not.
