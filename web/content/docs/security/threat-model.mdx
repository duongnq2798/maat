This page says what Maat protects, who can touch it, and what an attacker gets from each secret that could leak: what they can do, what they cannot, and what the response is. It is about the code and the tests as they are. The owner deployed the four Maat contracts on [Base](/docs/help/glossary#base) mainnet, so the owner key now controls a deployed vault and calendar. Since 2026-11-27 the agent runs in [live mode](/docs/help/glossary#live-mode) on Base mainnet, with the real Claude API, and the [CDP wallet](/docs/help/glossary#cdp-server-wallet) is the vault's executor. Its first `Decision`, at 02:14 UTC that day, was a buy the vault refused with `MARKET_CLOSED`. Before that, it had run in live mode only on a fork, with a scripted proposer and a local sender. Where a protection is untested against the real service, the row says so. [The security model](/docs/security/model) lists the rules themselves.

## Assets

| Asset | Where it lives | What protects it |
| --- | --- | --- |
| **The treasury**: USDC and [B20](/docs/help/glossary#b20) stocks | The [vault](/docs/help/glossary#vault). The design spec sizes the treasury at <Fact name="treasuryUsd" /> | The checks and caps on `execute`. Only the [owner](/docs/help/glossary#owner) can `withdraw`, and only to the owner address |
| **Collateral and debt** | The [Aave V4](/docs/help/glossary#aave-v4) position, held by the credit adapter | Only the vault can move the position (`onlyVault` in the adapter). The credit checks, and the [health factor](/docs/help/glossary#health-factor) floor on every borrow |
| **The rules** | The [mandate](/docs/help/glossary#mandate), each stock's settings and the [payee](/docs/help/glossary#payee) list | Owner-only, and changed only through the [timelock](/docs/help/glossary#timelock) of <Fact name="timelockHours" /> |
| **The owner role** | One address, set when the vault is created | It is immutable and no function transfers it |
| **The [executor](/docs/help/glossary#executor)'s gas** | A little ETH in the executor account. The agent README suggests sending <Fact name="executorGasEth" />, an estimate | The CDP account policy, which is untested against the real CDP. The vault's funds are not in this account |
| **The secrets** | The owner key, the executor key (held by the CDP wallet), the Claude API key, the CDP API key and wallet secret, and the RPC URL (`BASE_RPC_URL`, and `BASE_RPC_URL_FALLBACK` when it is set) | Outside the repository. The agent reads the Claude key, the CDP values and the RPC URL from its environment. The owner key stays in the owner's own wallet (`--account maat-owner` in the runbook), and the agent does not need it. `.env` files are git-ignored |
| **The agent's data folder** | `data/state.json` and `data/journal.jsonl`: unpaid bills, pending sends, the [journal](/docs/help/glossary#journal) | One agent per folder, enforced by a lock file. Tampering can make the agent skip or repeat a bill, not change what the vault allows |

## Actors

| Actor | Trusted? | What it can do | What it cannot do |
| --- | --- | --- | --- |
| **The owner** | Yes | Everything an owner function allows: pause, replace the executor, withdraw, fund, and queue, cancel or apply rule changes | Change the owner address, or apply a rule change before the timelock ends |
| **The executor** | No | Send [intents](/docs/help/glossary#intent) to `execute`, once per intent id | Call any owner function, or loosen a rule |
| **Claude** | No | Propose intents as data | Hold a wallet key, send a transaction, choose the verdict, set the slippage or pay a bill |
| **Whoever runs the agent host** | Holds the secrets in the agent's environment | Everything the Claude key, the CDP credentials and the RPC URL allow. The next section goes through them | Anything the owner key alone can do. The agent does not need the owner key |
| **Anyone onchain** | No | Call `notifyRevenue`, `syncMultiplier`, `previewIntent` and the views | Call `execute` or an owner function |
| **The calendar's owner** | Yes (it is the vault's owner) | Add a holiday or set an earlier close | Remove a holiday or loosen a close on that calendar. Loosening means pointing the mandate at a new calendar, which the vault's owner can do only through the timelock ([Holidays and early closes](/docs/concepts/market-hours#holidays-and-early-closes)) |
| **The token's issuer** | Outside Maat | Pause a B20 token's transfers, change its transfer policies, change its `uiMultiplier` | Make the vault trade through any of those: the vault refuses |
| **The RPC provider** | No | Answer the agent's reads, truthfully or not | Sign or send as the agent, or change a verdict |

## If a key leaks

Five secrets exist when Maat runs. For each, the table says what an attacker with only that secret can and cannot do, and the paragraph after it says what the response is. The responses are described, not scripted: the steps that need the owner's signature are in [Pause, withdraw, recover](/docs/guides/pause-withdraw-recover).

In short:

| Secret | Where it lives | What it reaches onchain | First response |
| --- | --- | --- | --- |
| [The owner key](/docs/security/threat-model#the-owner-key) | The owner's own wallet. The agent does not need it | Every owner function: `withdraw`, `setPaused`, `setExecutor`, `fund` and `cancelChange` at once, rule changes after the timelock, and the calendar's holidays and early closes | None onchain. Withdraw before the attacker does |
| [The executor key](/docs/security/threat-model#the-executor-key) | Held by the CDP wallet | `execute`, once per intent id, inside the mandate | The owner calls `setExecutor` with a new account, or `setPaused` |
| [The Claude API key](/docs/security/threat-model#the-claude-api-key) | The agent's environment | Nothing | Revoke it with Anthropic |
| [The CDP API key and wallet secret](/docs/security/threat-model#the-cdp-api-key-and-wallet-secret) | The agent's environment: `CDP_API_KEY_ID`, `CDP_API_KEY_SECRET` and `CDP_WALLET_SECRET` | What the executor key reaches, while the account policy holds. The policy is untested against the real CDP | Revoke them at CDP, then the owner calls `setExecutor` |
| [The RPC URL](/docs/security/threat-model#the-rpc-url) | The agent's environment | Nothing. It serves only the agent's reads, estimates and receipts | Replace it at the provider |

### The owner key

| The attacker can | but cannot |
| --- | --- |
| Withdraw every token the vault holds to the owner address, at once. `withdraw` does not wait for the timelock and the pause flag does not stop it | Change the owner address. It is immutable and no function transfers it |
| Make the owner address the executor, repay the debt, take the collateral back and then withdraw it. The collateral step works only if the token's transfer policy accepts that address (see [tx.origin in the policy check](/docs/security/not-claimed#txorigin-in-the-policy-check)) | Rewrite the contract code |
| Pause or unpause the vault, replace the executor with an address they control, and cancel a rule change the legitimate holder queued | |
| Queue and apply rule changes, which is the only owner action that waits | |

The timelock slows rule changes only, and a rule change is the slowest way to take the funds. There is no onchain response to a leaked owner key: the vault has no way to tell two holders of the same key apart, or to take the role away. The only response left is a race: the legitimate holder withdrawing before the attacker does. The README lists the single-key owner as a known limitation, and says that a multisig owner is compatible but not set up. No test plays a hostile owner, because the vault has no defense to test.

### The executor key

This is the case the vault is built for. Say an attacker controls the server that runs the agent:

| The attacker can | but cannot |
| --- | --- |
| Call `execute` with any intent, once per intent id | Skip any of the <Fact name="checksPerTrade" /> checks on a `BUY` or a `SELL` (check 9, concentration, is `BUY` only; the other actions have their own), trade outside the session or the stock list, or beat the per-trade cap (<Fact name="mandate.perTradeCapUsd" />) or the daily cap (<Fact name="mandate.dailyCapUsd" />) with a trade or a bill payment |
| Make bad but allowed trades inside the mandate, every UTC day until the key is replaced. That includes timing a swap so that a pool trade of their own lands just before it, and gaining from the worse fill. The [slippage floor](/docs/help/glossary#slippage-floor) bounds that at `maxSlippageBps` of the swap's oracle value: under the default mandate, at most <Fact name="slippageLossPerTradeUsd" /> a trade and <Fact name="slippageLossPerDayUsd" /> a day ([A manipulated pool price or a bad fill](/docs/security/threat-model#other-threats)) | Send funds anywhere: swaps go to the allowlisted pool, borrowed USDC and collateral come back to the vault, and `PAY_EXPENSE` pays only allowlisted payees |
| Pay an allowlisted payee, up to the same caps | Pay any other address: the vault returns `PAYEE_NOT_ALLOWED` |
| Supply stock to Aave, borrow USDC against it and leave the debt open | Push the projected health factor below the floor (<Fact name="mandate.minHealthFactor" />), or below the target (<Fact name="mandate.targetHealthFactor" />) inside the [de-risk window](/docs/help/glossary#de-risk-window), at the moment of the borrow |
| Stop sending intents | Change the mandate, withdraw, unpause, or keep the key once the owner replaces it |

Two things in the left column are worth reading twice. The caps bound each UTC day and not the whole episode: a stolen key can spend up to the daily cap every day until the owner notices, so the total depends on how fast that is. And a borrow is checked when it is made. A loan at the floor is still a loan with interest, and a fall in the stock's price afterwards lowers its health factor without the vault doing anything.

**Blast radius.** This is what a stolen executor key can cost on each path, with the default mandate. Each row follows from the vault's code, and the tests named in it show the rule it rests on.

| Path | What it can cost | Why, in the code | Shown by |
| --- | --- | --- | --- |
| **Trades** (`BUY`, `SELL`) | Roughly the slippage limit (<Fact name="mandate.maxSlippageBps" />) on the daily cap (<Fact name="mandate.dailyCapUsd" />) per UTC day, measured against the oracle | Every swap must return at least the oracle-implied amount less `maxSlippageBps`, whatever `minOut` the intent carries (`_perform`). A `BUY` counts its USDC and a `SELL` the oracle value of its stock toward `spentOnDay`, which cannot pass the daily cap (`_withinCaps`). So an attacker who also trades against the pool can take at most the slippage on at most the daily cap. It is rough because the reference is the oracle: it may lag the market for up to `maxStaleness` (<Fact name="mandate.maxStalenessSec" />), and the pool's TWAP may sit up to `maxPremiumBps` (<Fact name="mandate.maxPremiumBps" />) away from it, so against the TWAP the bound is closer to the slippage limit plus the premium limit on the daily cap | [`test_slippageFloorIsEnforcedEvenIfAgentSendsZero`](https://github.com/duongnq2798/maat/blob/main/contracts/test/MandateVault.t.sol), [`test_dailyCap`](https://github.com/duongnq2798/maat/blob/main/contracts/test/MandateVault.t.sol) |
| **`PAY_EXPENSE`** | Up to the daily cap per UTC day, if an allowlisted payee's key sits on the agent's host | A payment needs an allowlisted payee, then counts toward the same per-trade cap (<Fact name="mandate.perTradeCapUsd" />) and daily cap as a trade (`_checkExpense`). A payee the attacker also controls, such as a wallet kept on the same server, can receive the whole daily cap every day in pieces no larger than the per-trade cap. Trades and payments share one daily cap, so this row and the one above do not add up | [`test_payExpenseRejectsUnknownPayee`](https://github.com/duongnq2798/maat/blob/main/contracts/test/MandateVault.t.sol), [`test_payExpenseSharesDailyCapWithTrades`](https://github.com/duongnq2798/maat/blob/main/contracts/test/MandateVault.t.sol) |
| **Credit** (`BORROW`, and `WITHDRAW_COLLATERAL` against debt) | No size cap: debt down to the minimum health factor (<Fact name="mandate.minHealthFactor" />), or to the target (<Fact name="mandate.targetHealthFactor" />) inside the de-risk window | Credit actions count toward neither cap (`_checkCredit`). A borrow needs an open market, healthy collateral and a projected health factor at or above the floor, and the adapter checks the floor again after a borrow or a withdrawal. The borrowed USDC lands in the vault, where only the two rows above can move it to anyone but the credit adapter (a `REPAY` pays the debt down), but the debt accrues interest, and a later fall in the stock's price can bring the position to liquidation | [`test_borrowRefusals`](https://github.com/duongnq2798/maat/blob/main/contracts/test/MandateVaultCredit.t.sol), [`test_borrowSendsUsdcToVault`](https://github.com/duongnq2798/maat/blob/main/contracts/test/MandateVaultCredit.t.sol) |

The day in these rows is a UTC day, not a rolling 24 hours, so the daily cap can be spent just before midnight and again just after it. The [invariant suite](/docs/security/testing#invariant-tests) checks the daily cap on every UTC day it touches, midnight crossings included, and that USDC leaves the vault only to an adapter or an allowlisted payee.

**Response.** The owner replaces the executor, which is instant and stops the old key at once ([`test_rotatingExecutorRevokesOldOne`](https://github.com/duongnq2798/maat/blob/main/contracts/test/MandateVaultAdmin.t.sol)), or pauses the vault. A paused vault still accepts `REPAY`, so debt can be paid down ([`test_repayIsAllowedWhileVaultPaused`](https://github.com/duongnq2798/maat/blob/main/contracts/test/MandateVaultCredit.t.sol)). The steps are in the guide above.

`test_compromisedExecutorIsBounded` in [MandateVaultFork.t.sol](https://github.com/duongnq2798/maat/blob/main/contracts/test/fork/MandateVaultFork.t.sol) plays this attacker against real [Base](/docs/help/glossary#base) state at block <Fact name="forkBlock" />. | What the test tries as the executor | Result |
| --- | --- |
| `PAY_EXPENSE` to an address that is not a payee | Refused with `PAYEE_NOT_ALLOWED` |
| A `BUY` above the per-trade cap | Refused with `SIZE_LIMIT` |
| `withdraw` | [Reverts](/docs/help/glossary#revert) with `NotOwner` |

At the end the attacker address holds nothing and the vault holds all the USDC it started with. The test does not try a borrow, because the vault has no credit adapter there. The borrow row of the table is covered by the credit unit tests instead: [`test_borrowRefusals`](https://github.com/duongnq2798/maat/blob/main/contracts/test/MandateVaultCredit.t.sol) shows the floor and [`test_deriskWindowRequiresTargetHealthFactor`](https://github.com/duongnq2798/maat/blob/main/contracts/test/MandateVaultCredit.t.sol) shows the target, both with a mock credit adapter, and the adapter's own [fork test](/docs/help/glossary#fork-test) shows that a borrow below the minimum health factor reverts. The caps are the default mandate's, and the owner can set others.

### The Claude API key

| The attacker can | but cannot |
| --- | --- |
| Make calls that are billed to the account that owns the key | Move, read or change anything in the vault, or sign or send a transaction |
| Use up the account's limits so that the agent's own calls fail | Change what the agent proposes. The agent makes its own calls, and the key only authenticates them |

The vault pays only for the usage the agent counted. The agent computes each cost from the `usage` in its own responses, so calls made by someone else are not on the bill that the vault pays. If the agent's calls fail for any reason, including a revoked key, the proposer returns no proposals and does not throw ([`proposer.test.ts`](https://github.com/duongnq2798/maat/blob/main/agent/test/proposer.test.ts): "never throws on an API error"). The [round](/docs/help/glossary#round) then proposes no trades, but a bill that is due is still queued, because `runOnce` adds it before it looks at Claude's answer.

**Response.** Revoke the key with Anthropic, create a new one and put it in the agent's environment. The key never reaches the chain, so nothing onchain needs to change. In the tests the proposer's calls run only against a fake client; since 2026-11-27 the live agent calls the real Claude API with the owner's key.

### The CDP API key and wallet secret

The agent reads three values for the CDP Server Wallet: `CDP_API_KEY_ID`, `CDP_API_KEY_SECRET` and `CDP_WALLET_SECRET`. The repository does not say which of the three CDP needs for which call, so this page treats them as one secret.

| The attacker can | but cannot |
| --- | --- |
| Act as the executor: ask CDP to send or sign transactions from the executor account, which is the same position as the executor-key row above | While the account policy holds: send a transaction anywhere but the vault, on any network but Base, or with any value; sign a transaction to any address but the vault, or with any value (the sign rule has no network limit); or sign a hash, a message or typed data |
| Get a signature from the executor account in any way CDP enforces the policy differently from what its rules say. The policy rejects `signEvmHash`, `signEvmMessage` and `signEvmTypedData`, and no test shows that CDP enforces it | Use such a signature on the vault. No vault function reads a signature: `execute` checks only that the caller is the executor |
| Call any function of the vault from that account | Make any function other than `execute` do more than anyone could: the rest are public and harmless, or revert `NotOwner` |

The policy is attached by `cdp-setup.ts`, with the same three values. The repository does not show whether CDP would let a holder of these values change or detach the policy, and these docs record no send that the real CDP blocked: the live agent's first `Decision` went through it on 2026-11-27, a send the policy allows, the code is tested against a fake client, and [`cdpPolicy.test.ts`](https://github.com/duongnq2798/maat/blob/main/agent/test/cdpPolicy.test.ts) checks the shape of the rules and parses them with the CDP SDK's own schema, not that CDP enforces them. So do not count on the policy as the only barrier. If the policy could be removed, the worst case would still be the executor account's own ETH, because the vault's funds are not in that account.

**Response.** Two halves. Revoke the CDP API key and wallet secret wherever you created them (Maat's scripts cannot do this for you). In the vault, the owner replaces the executor with `setExecutor`, pointing at a new account, so that the old account can no longer call `execute`. When it is unclear whether someone else still controls the old account, the second half is the one that stops it, and it is instant.

### The RPC URL

| The attacker can | but cannot |
| --- | --- |
| Send requests on your quota, and so on your bill | Sign or send a transaction as the agent. The agent sends through CDP, and the RPC only serves its reads, estimates and receipts |
| Make the agent's reads fail by using up the quota | Read anything that is not public chain data, or change a verdict |

With `BASE_RPC_URL_FALLBACK` set, a used-up quota moves the agent's reads to that second URL first. If the agent cannot read the vault's state, it does nothing for that round ([`runOnce.test.ts`](https://github.com/duongnq2798/maat/blob/main/agent/test/runOnce.test.ts): "does nothing when the vault state is unavailable"). That is a stop, not a risk to funds.

**Response.** Replace the URL at your provider and update the agent's environment. The optional second URL, `BASE_RPC_URL_FALLBACK`, is a secret of the same kind, and the same response applies to it. This is a leaked URL. A provider that answers dishonestly is a different case, and the next section covers it.

## Other threats

| Threat | What bounds it | What it does not cover |
| --- | --- | --- |
| **A bad Claude proposal**, from a wrong idea or from wrong numbers in what it reads ([What Claude reads](/docs/security/threat-model#what-claude-reads)) | The schema and the clamps in the agent, then the mandate: the session, the stock list, the caps, concentration and the health factor. Claude cannot set the slippage, choose a payee or pay a bill | A bad trade inside every limit is allowed. The vault does not judge whether a trade is a good idea |
| **A stale price** | Check 5 refuses a feed answer that is not positive, or is older than `maxStaleness` (<Fact name="mandate.maxStalenessSec" /> by default): `FEED_STALE` or `BAD_PRICE`. For a buy or a sell, check 7 also refuses once the pool drifts more than `maxPremiumBps` from a frozen answer | Within that age, the vault trades on the last published price while the pool stays near it. A borrow, or a withdrawal against debt, has no premium check |
| **A manipulated pool price or a bad fill** | Check 7 refuses a pool [TWAP](/docs/help/glossary#twap) (<Fact name="mandate.twapWindowSec" /> window) that is more than `maxPremiumBps` (<Fact name="mandate.maxPremiumBps" /> by default) from the oracle. The slippage floor, set from the oracle (<Fact name="mandate.maxSlippageBps" /> by default), makes a swap that returns less fail with `SWAP_FAILED`. Under the default mandate, a swap at the per-trade cap can fill at most <Fact name="slippageLossPerTradeUsd" /> below its oracle value, and one UTC day's swaps at most <Fact name="slippageLossPerDayUsd" />, because the daily cap counts buys, sells and bill payments | A pool price inside the [premium](/docs/help/glossary#premium) limit is accepted. Check 7 reads the TWAP, not the pool's spot price at the swap, and the adapter swaps with the widest price limit and checks the output only against `minOut`. So any fill down to the floor is accepted: anyone who trades the pool just before the swap, as a sandwich attack does (a kind of MEV, maximal extractable value), can push it there, up to `maxSlippageBps` of the swap's oracle value. The bound is relative to the oracle, and a wrong but fresh oracle price is trusted |
| **A missed holiday** | Only the price checks. A day missing from the calendar counts as a normal session, so check 4 passes. Check 5 refuses once the last answer is older than `maxStaleness` ([staleness](/docs/help/glossary#staleness)), and, for a buy or a sell, check 7 refuses if the pool's TWAP drifts more than `maxPremiumBps` from that answer | Until then, and while the pool stays inside the premium limit, the vault can trade on the last answer. With the default staleness limit, the last answer may stay under it for the whole holiday, and a borrow, or a withdrawal against debt, has no premium check. The owner has to add the day ([What happens if a holiday is missing](/docs/concepts/market-hours#what-happens-if-a-holiday-is-missing)) |
| **A split or a dividend** | Check 6 blocks a stock when its multiplier differs from the vault's snapshot, has a change scheduled, or is inside the cooldown after a change | The assumption that the feed already includes the multiplier has not been observed across a real split |
| **The issuer pauses or restricts a token** | Checks 2 and 3 refuse with `TOKEN_PAUSED` or `POLICY_BLOCKED` | The vault can only refuse. It cannot move a token that the token itself will not transfer |
| **A dishonest or failing RPC** | The vault does not use it: a verdict is computed in the transaction. The agent [previews](/docs/help/glossary#preview) as the executor. If the vault refuses an intent the preview passed, the agent records a mismatch and halts the round ([`runOnce.test.ts`](https://github.com/duongnq2798/maat/blob/main/agent/test/runOnce.test.ts): "halts when the preview said OK but the vault refused"). A [refusal](/docs/help/glossary#refusal) sent only to be logged that comes back with another reason is recorded as a mismatch, and the round goes on ("journals a log-refusal whose reason differs and continues"). A halt ends that round only: when the agent runs without `--once` ([Agent scripts](/docs/reference/agent-scripts#agent)), the next round starts on the usual schedule | A lying RPC can mislead the agent's bookkeeping, for example report a payment that landed as missing, so that the agent later pays the same bill again. The daily cap bounds that amount |
| **A lost owner key** | Nothing. No function replaces the owner | Nobody can pause, replace the executor, withdraw or change a rule. The executor keeps working inside the mandate, and if its key leaks later nobody can stop it |
| **A bug in the contracts or the agent** | The tests, which [How it is tested](/docs/security/testing) lists | There is no third-party audit. See [What Maat does not claim](/docs/security/not-claimed) |

### What Claude reads

The agent sends Claude a system prompt and one user message, both built in [`prompt.ts`](https://github.com/duongnq2798/maat/blob/main/agent/src/llm/prompt.ts): `systemPrompt`, fixed text apart from its credit lines, which follow `MAAT_CREDIT_ACTIONS`, and `renderUserMessage`. The request gives Claude no tools. This is the whole user message of a round without briefs:

```typescript title="agent/src/llm/prompt.ts#L62-L111"
export function renderUserMessage({ state: s, policy: p, billUsd6, creditActions }: ProposerInput): string {
  const view = {
    block: s.blockNumber.toString(),
    utcTime: new Date(Number(s.timestamp) * 1000).toISOString(),
    marketOpen: s.marketOpen,
    maxStalenessSec: s.mandate.maxStaleness,
    vaultPaused: s.paused,
    creditActions: creditActions ? "on" : "off",
    usdc: usd(s.usdcBalance),
    newRevenue: usd(s.newRevenue),
    equity: usd(p.equityUsd6),
    cashWeightPct: p.cashBps / 100,
    unpaidComputeBill: usd(billUsd6),
    computeRunwayNeed: usd(p.runwayNeedUsd6),
    spendableForTrades: usd(p.spendableUsd6),
    credit: s.credit && {
      readable: s.credit.readable,
      debt: usd(s.credit.debt),
      healthFactor: s.credit.debt === 0n ? null : Number(s.credit.healthFactor) / 1e18,
      minHealthFactor: Number(s.mandate.minHealthFactor) / 1e18,
      targetHealthFactor: Number(s.mandate.targetHealthFactor) / 1e18,
      // The last seconds before 20:00 ET on a Friday or before a holiday, in which a credit action that adds risk must
      // leave targetHealthFactor rather than minHealthFactor (MandateVault._inDeriskWindow, DERISK_WINDOW).
      deriskWindowSec: s.mandate.deriskWindow,
    },
    // The thresholds the vault checks a trade against, from its mandate() and tokenConfig() at the state block, and
    // today's spend so far, from spentOnDay(today).
    limits: {
      perTradeUsd: usd(s.mandate.perTradeCapUsd),
      dailyUsd: usd(s.mandate.dailyCapUsd),
      spentTodayUsd: usd(s.spentToday),
      sessionMode: SESSION_MODES[s.mandate.sessionMode] ?? s.mandate.sessionMode,
      maxPremiumBps: s.mandate.maxPremiumBps,
      maxSlippageBps: s.mandate.maxSlippageBps,
      maxWeightPct: Object.fromEntries(s.tokens.map((t) => [t.symbol ?? t.address, t.config.maxWeightBps / 100])),
    },
    tokens: s.tokens.map((t) => ({
      symbol: t.symbol ?? t.address,
      price: t.price8 === null ? null : Number(t.price8) / 1e8,
      feedAgeSeconds: t.feedAge === null ? null : Number(t.feedAge),
      valueUsd: usd(t.valueUsd6),
      ...(() => {
        const w = p.weights.find((x) => x.symbol === t.symbol);
        return w ? { weightPct: w.weightBps / 100, targetPct: w.targetBps / 100, inVaultUsd: usd(w.walletUsd6), suppliedUsd: usd(w.suppliedUsd6) } : {};
      })(),
    })),
    suggestions: p.suggestions.map((x) => ({ action: x.action, symbol: x.symbol, amountUsd: usd(x.amountUsd6), why: x.why })),
  };
  return `Current state:\n${JSON.stringify(view, null, 2)}\n\nDecide this round's actions.`;
}
```

It holds three kinds of input, all numbers, flags, addresses, fixed names or text the agent builds from them, and no text from outside the agent. Briefs, below, are the one exception:

- **The vault's state**, read through the RPC at one block: the USDC balance and new revenue, each stock's price, feed age and value, the market and pause flags, the caps and today's spend, the session mode, the staleness, premium and slippage limits, each stock's concentration limit, and the Aave position with the derisk window.
- **The agent's own unpaid Claude bill**, from its data folder.
- **The rule-based policy's view**: equity, weights, the [runway](/docs/help/glossary#runway) it wants and its suggestions, which the agent computes from those numbers and from the Claude costs its data folder records for the week before today (`MAAT_DEFAULT_DAILY_COMPUTE_USD` when there are none). Each suggestion's `why` is built from numbers and fixed symbols.

It also says whether credit actions are on, from `MAAT_CREDIT_ACTIONS`.

Token names come from a fixed list (`BASKET` in `agent/src/addresses.ts`), and a token that is not on it appears as its address. The agent fetches no news, social post or web page: its only network clients are the RPC, the Claude API and, in live mode, CDP. So, without briefs, the way to mislead Claude is with wrong numbers, for example from a dishonest RPC, not with written instructions. Its answer must match the proposal schema, or the whole answer is rejected. This describes the code; the agent has called the real Claude API in live mode only since 2026-11-27.

**Briefs.** In an agent built from `main`, once `deployments/README.md` records MaatInbox, a round may carry [briefs](/docs/guides/brief-the-agent), public text anyone can post. The table has recorded it since 2026-11-27, but the agent that runs on Maat's vault now, from the tag `agent-r2`, predates briefs and sends Claude none. `briefSystemPrompt` then adds rules that call a brief untrusted data, and `renderBriefMessage` adds a section marked untrusted, between marker lines with a random nonce, with one `{id, from, text}` JSON line per brief. In `text` every Cc, Cf and Default_Ignorable code point is U+FFFD, and U+2028 and U+2029 are JSON escapes, so a brief cannot end its line or the section. Caps and a daily brief budget bound how many briefs reach Claude and how many brief-driven transactions go out ([Briefs](/docs/guides/run-the-agent#briefs)). A brief that persuades Claude is expected, so the vault is the boundary: every intent still meets its checks, each Claude intent's blob in that round is a fixed template of typed fields, and Claude's replies go to the journal only, sanitized. A bad brief id or reply drops that item, not the answer.

## Mitigations you run

The code cannot do these for you. They are advice, they are not enforced and none of them has a test.

- **Keep the owner key off the agent's host.** No script in the repository holds a key. The transactions the owner signs, among them `fund`, `setPaused`, `setExecutor`, `withdraw`, every rule change and the calendar's holidays, are meant to be signed from the owner's own wallet (`--account maat-owner` in the runbook). The agent's `execute` calls are signed by the CDP executor account, and the agent does not need the owner key to run.
- **Check the owner address before you deploy.** It is immutable. A typo is permanent. [Deploy your own vault](/docs/guides/deploy-your-own-vault) has the checklist.
- **Consider a multisig as the owner.** The contract is compatible with one and Maat has not set one up. The owner is fixed at deployment, so the choice is made then.
- **Keep secrets out of the repository.** Put the Claude key, the CDP values and the RPC URL in the agent's `.env` or in your secret store, and never paste a real RPC URL into an issue or a doc.
- **Fund the executor with gas only.** Its account should hold nothing else.
- **Start with a [dry run](/docs/help/glossary#dry-run).** It reads the chain, calls Claude and sends nothing, so you can read the journal before anything is signed. It still costs real API fees.
- **Watch the decisions.** An unexpected `allowed=true`, or a run of refusals, is the signal. [Watch decisions onchain](/docs/guides/watch-decisions-onchain) shows how.
- **Watch for queued changes you did not make.** A `MandateChangeQueued`, `TokenConfigChangeQueued` or `PayeeChangeQueued` event that you did not cause means someone else holds the owner key. It is a warning, not a defense: that key can also withdraw at once, and `withdraw`, `setPaused` and `setExecutor` give no notice. [Events](/docs/reference/events) lists them.
- **Keep the calendar current.** Add each holiday before the day. A missed one leaves only the price checks, the staleness and premium limits, to stop a trade.
- **Know the response before you need it.** Read [Pause, withdraw, recover](/docs/guides/pause-withdraw-recover) while nothing is wrong.
- **Keep the treasury small.** The design spec sizes it at <Fact name="treasuryUsd" />, and the caps are in the same range.
