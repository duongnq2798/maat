This page says what exists, what comes next and what is only an idea, so you can tell a claim about Maat from a plan. Maat is unaudited and is not deployed on Base mainnet yet. Everything built so far has been tested. The contracts and the agent's send path have also run on a local [fork](/docs/help/glossary#fork-test) of Base mainnet.

## Next: mainnet

<DeploymentTable />

The owner deploys by hand. Every deploy, funding and setup transaction is signed from the owner's own wallet, and no script in the repository holds a key. The checklist, in order:

1. **Deploy.** Simulate with the real configuration and check the printed owner address character for character, because the owner is immutable. Then broadcast. The commands are in [Deploy your own vault](/docs/guides/deploy-your-own-vault).
2. **Fund.** Approve the USDC, then call `fund(amount)` on the vault. Do not transfer USDC straight into it, because `notifyRevenue` would record that as revenue.
3. **Run the owner's smoke test.** At first the owner's own wallet is the executor. While it is, the owner signs one small buy during US market hours, which must be allowed, and one buy on a weekend, which must be refused with `MARKET_CLOSED`. For Maat's own vault, [deployments/go-live.md](https://github.com/duongnq2798/maat/blob/main/deployments/go-live.md), steps 7 and 8, sends both buys with the calldata that `agent/scripts/first-decision.ts` builds, which ends with the Builder Code. [Run the smoke test](/docs/guides/deploy-your-own-vault#run-the-smoke-test) gives plain commands, with no Builder Code, for a vault of your own. A [credit smoke test](/docs/guides/deploy-your-own-vault#run-the-credit-smoke-test) follows the same way. The addresses and transaction hashes then go into the table in `deployments/README.md`, which the start of this section reads.
4. **Hand the executor role to the CDP wallet.** The agent's `cdp-setup.ts` script creates the CDP executor account, or finds the one named by `CDP_ACCOUNT_NAME` (`maat-executor` by default), attaches its policy and prints its address. The owner then calls `setExecutor` with that address, sends <Fact name="executorGasEth" /> on Base to it for gas, and sets `MAAT_EXECUTOR` in `agent/.env`. [Run the agent](/docs/guides/run-the-agent#go-live) has the owner-only steps. After the handover the owner's own `execute` calls revert with `NotExecutor`, which is why the smoke test comes first.
5. **Record the agent's first real `Decision`.** [Live mode](/docs/help/glossary#live-mode) needs a registered Builder Code and CDP keys, which the owner sets up. Once the agent runs in live mode on the mainnet vault, the first `Decision` it records is the first one signed through the CDP wallet.

Until the owner deploys, no page in these docs is labeled live, and the site's ledger shows only the fork run.

## Planned, not built

<Callout type="note" title="Planned">

None of this is on `main`. Each item links the spec section it is sketched in and names the dependencies that spec states. W2 and W3 are the next two stages of the website, as the web design spec lays them out.

1. **A mainnet ledger, a dashboard and a Base App mini-app manifest (W2).** The ledger would read `Decision` events from the mainnet vault and link each row to Basescan. Where the operator exports the agent's [journal](/docs/help/glossary#journal), it would show the [rationale](/docs/help/glossary#rationale) text, with a "hash verified" badge only when `keccak256` of the text equals the `rationaleHash` onchain. It needs the mainnet deploy first. Sketched in [the web design spec, section 10](https://github.com/duongnq2798/maat/blob/main/docs/superpowers/specs/2026-11-07-maat-web-design.md#10-web-roadmap-after-w1-each-part-has-its-own-spec).
2. **An [x402](/docs/help/glossary#x402) Guard Service.** Other agents would pay <Fact name="x402Price" /> per "is this trade safe now?" check, and that USDC would fund the treasury loop. It is not on `main`; [pull request #2](https://github.com/duongnq2798/maat/pull/2), open and unmerged, adds it. The design pays the vault's address, so it needs a deployed vault. The spec leaves open whether the CDP x402 facilitator can pay a contract directly; if it cannot, the payment goes to the agent wallet, which forwards it to the vault. Sketched in [the treasury design spec, section 3.4](https://github.com/duongnq2798/maat/blob/main/docs/superpowers/specs/2026-11-06-mandate-treasury-design.md#34-guard-service-typescript-viem).
3. **A Guard Service HTTP API, an MCP server and a Bankr Skill** that expose the same check. The spec names two MCP tools, `market_status` and `check_trade`, and calls the MCP server and the Bankr Skill stretch goals. The Guard Service and its HTTP API are part of pull request #2; the MCP server and the Bankr Skill are not. Sketched in [the treasury design spec, section 3.4](https://github.com/duongnq2798/maat/blob/main/docs/superpowers/specs/2026-11-06-mandate-treasury-design.md#34-guard-service-typescript-viem).
4. **`MandateFactory`.** Any agent would deploy its own vault with its own mandate. It is a stretch goal. The sketch deploys each vault as an EIP-1167 clone, which does not fit the current `MandateVault`: it sets its owner, USDC and policy registry as immutables in its constructor and has no initializer. Sketched in [the treasury design spec, section 3.7](https://github.com/duongnq2798/maat/blob/main/docs/superpowers/specs/2026-11-06-mandate-treasury-design.md#37-mandatefactory-stretch-week-3).
5. **A daily diary and a replay page for the fork scenarios (W3).** Sketched in [the web design spec, section 10](https://github.com/duongnq2798/maat/blob/main/docs/superpowers/specs/2026-11-07-maat-web-design.md#10-web-roadmap-after-w1-each-part-has-its-own-spec).

</Callout>

## How this page stays honest

- Every page sets its label in its frontmatter, and a test rejects any value other than the three above.
- Nothing is labeled live until the owner deploys. The start of [Next: mainnet](#next-mainnet) is read from the table in `deployments/README.md`. Once a Base mainnet row of that table has an address, a test fails and lists each line, on the docs pages and in the note of the ABI JSON files, that still says Maat has no deployment in one of the phrases it looks for.
- A page fails a test if its text outside the frontmatter, code and the attributes of component tags types out by hand a fact, one of the named values the docs render with `<Fact>`, that contains three or more digits in a row (dates aside), a dollar amount or a [bps](/docs/help/glossary#basis-point-bps) value. Tests check most facts against the contracts, the agent and the fork-run gas log. A few cite documents instead: the planned x402 price and the treasury size cite the treasury design spec, and the AMZNc pool liquidity cites the README and that spec. The check count cites that spec too, and its only test compares it with the site's own list of check labels, not with the contract.
- Test counts are not shown, because they go stale. The [Quickstart](/docs/get-started/quickstart) shows how to run the suites yourself.
- The date at the top of each page except the docs home, Last reviewed, says when the page was last checked against its sources.
