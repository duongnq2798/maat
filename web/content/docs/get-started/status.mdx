This page says what exists, what comes next and what is only an idea, so you can tell a claim about Maat from a plan. The owner deployed the four Maat contracts to Base mainnet, at the addresses under [Next: mainnet](#next-mainnet), and they are unaudited. Everything built so far has been tested. The contracts and the agent's send path have also run on a local [fork](/docs/help/glossary#fork-test) of Base mainnet, and the agent has run in [live mode](/docs/help/glossary#live-mode) only on a fork.

## Next: mainnet

<DeploymentTable />

On 2026-11-24, the Contract tab of each of the four contracts on Basescan showed its source as verified, with an exact match: the deployed bytecode matches the source submitted for it. A verified source is not an audit.

The owner deploys by hand. Every deploy, funding and setup transaction is signed from the owner's own wallet, and no script in the repository holds a key. The checklist, in order:

1. **Deploy.** The table above records this step for the four Maat contracts. To deploy, simulate with the real configuration and check the printed owner address character for character, because the owner is immutable. Then broadcast. The commands are in [Deploy your own vault](/docs/guides/deploy-your-own-vault).
2. **Fund.** Approve the USDC, then call `fund(amount)` on the vault. Do not transfer USDC straight into it, because `notifyRevenue` would record that as revenue.
3. **Run the owner's smoke test.** At first the owner's own wallet is the executor. While it is, the owner signs one small buy during US market hours, which must be allowed, and one buy on a weekend, which must be refused with `MARKET_CLOSED`. For Maat's own vault, [deployments/go-live.md](https://github.com/duongnq2798/maat/blob/main/deployments/go-live.md), steps 7 and 8, sends both buys with the calldata that `agent/scripts/first-decision.ts` builds, which ends with the Builder Code. [Run the smoke test](/docs/guides/deploy-your-own-vault#run-the-smoke-test) gives plain commands, with no Builder Code, for a vault of your own. A [credit smoke test](/docs/guides/deploy-your-own-vault#run-the-credit-smoke-test) follows the same way.
4. **Hand the executor role to the CDP wallet.** The agent's `cdp-setup.ts` script creates the CDP executor account, or finds the one named by `CDP_ACCOUNT_NAME` (`maat-executor` by default), attaches its policy and prints its address. The owner then calls `setExecutor` with that address, sends <Fact name="executorGasEth" /> on Base to it for gas, and sets `MAAT_EXECUTOR` in `agent/.env`. [Run the agent](/docs/guides/run-the-agent#go-live) has the owner-only steps. After the handover the owner's own `execute` calls revert with `NotExecutor`, which is why the smoke test comes first.
5. **Record the agent's first real `Decision`.** [Live mode](/docs/help/glossary#live-mode) needs a registered Builder Code and CDP keys, which the owner sets up. Once the agent runs in live mode on the mainnet vault, the first `Decision` it records is the first one signed through the CDP wallet.

After the deploy, these docs record only the vault's first two `Decision` events, the two buys of the owner's smoke test of step 3. The first is the refusal, sent on a weekday before the US market opened rather than on a weekend. In transaction [`0xdfdb6739...6c3b`](https://basescan.org/tx/0xdfdb6739912a73542d90129bd7269a939dc8b2d47a869f56d9ab5e3a02e86c3b), block `61700601`, at 2026-11-24 14:28:15 UTC, the owner, as the executor, sent a `BUY` of 5 USDC of NVDAc (`amount` `5000000`), and the vault refused it because the market was closed: `allowed` is `false` and `reason` is `6`, `MARKET_CLOSED`, for the intent id `0xdc06ec8e...243c`. The second is the in-session buy. In transaction [`0x61622340...23c8`](https://basescan.org/tx/0x61622340a151c73c3f2b3bc910292a3e3136bd4aa7ecd55a92f59914953a23c8), block `61745836`, at 2026-11-24 16:59:02 UTC, the owner, as the executor, sent the same `BUY` of 5 USDC of NVDAc with a new intent id, `0x475efb77...ee3d`, and the vault allowed it: `allowed` is `true` and `reason` is `0`, `OK`. The vault swapped the USDC on the NVDAc pool and received `3311718` NVDAc units (NVDAc has 8 decimals, so `0.03311718` NVDAc), and after that block it held `15000000` USDC units. The owner sent both buys with `deployments/go-live.md` and the calldata that `agent/scripts/first-decision.ts` builds, not through the agent runtime, and the calldata of each ends with the Builder Code suffix. Steps 2 to 5 each call the vault, so each one shows in the vault's history on Basescan, and every `Decision` the vault emits is public in its events there. No page in these docs is labeled live. The landing page's ledger shows only the fork run; the site's [mainnet ledger](/ledger) reads the vault's `Decision` events from Base in the browser.

## Planned, not built

<Callout type="note" title="Planned">

None of this is on `main`. Each item links the spec section it is sketched in and names the dependencies that spec states. The first item finishes the website's W2 stage; W3 is the stage after it, as the web design spec lays them out.

1. **A rationale store the agent writes as it runs (W2 follow-up).** The [mainnet ledger](/ledger) reads [rationale](/docs/help/glossary#rationale) text from a file the operator exports from the agent's [journal](/docs/help/glossary#journal) and commits, so new text appears only after the site is rebuilt. The plan is a database table the agent writes each rationale to and the page reads through the same interface; the page still shows the text only when `keccak256` of it equals the `rationaleHash` onchain. The Base App mini-app manifest of the first W2 sketch is dropped: the ledger is read-only and needs no wallet. Sketched in [the W2 ledger spec, section 10](https://github.com/duongnq2798/maat/blob/main/docs/superpowers/specs/2026-11-20-maat-web-w2-ledger-design.md#10-follow-ups-separate-tasks).
2. **An [x402](/docs/help/glossary#x402) Guard Service.** Other agents would pay <Fact name="x402Price" /> per "is this trade safe now?" check, and that USDC would fund the treasury loop. It is not on `main`; [pull request #2](https://github.com/duongnq2798/maat/pull/2), open and unmerged, adds it. The design pays the vault's address, so it needs a deployed vault. The spec leaves open whether the CDP x402 facilitator can pay a contract directly; if it cannot, the payment goes to the agent wallet, which forwards it to the vault. Sketched in [the treasury design spec, section 3.4](https://github.com/duongnq2798/maat/blob/main/docs/superpowers/specs/2026-11-06-mandate-treasury-design.md#34-guard-service-typescript-viem).
3. **A Guard Service HTTP API, an MCP server and a Bankr Skill** that expose the same check. The spec names two MCP tools, `market_status` and `check_trade`, and calls the MCP server and the Bankr Skill stretch goals. The Guard Service and its HTTP API are part of pull request #2; the MCP server and the Bankr Skill are not. Sketched in [the treasury design spec, section 3.4](https://github.com/duongnq2798/maat/blob/main/docs/superpowers/specs/2026-11-06-mandate-treasury-design.md#34-guard-service-typescript-viem).
4. **`MandateFactory`.** Any agent would deploy its own vault with its own mandate. It is a stretch goal. The sketch deploys each vault as an EIP-1167 clone, which does not fit the current `MandateVault`: it sets its owner, USDC and policy registry as immutables in its constructor and has no initializer. Sketched in [the treasury design spec, section 3.7](https://github.com/duongnq2798/maat/blob/main/docs/superpowers/specs/2026-11-06-mandate-treasury-design.md#37-mandatefactory-stretch-week-3).
5. **A daily diary and a replay page for the fork scenarios (W3).** Sketched in [the web design spec, section 10](https://github.com/duongnq2798/maat/blob/main/docs/superpowers/specs/2026-11-07-maat-web-design.md#10-web-roadmap-after-w1-each-part-has-its-own-spec).

</Callout>

## How this page stays honest

- Every page sets its label in its frontmatter, and a test rejects any value other than the three above.
- The start of [Next: mainnet](#next-mainnet) is read from the table in `deployments/README.md`. That table records the Base mainnet addresses of the four Maat contracts, so a test fails and lists each line, on the docs pages and in the note of the ABI JSON files, that says Maat has no deployment in one of the phrases it looks for.
- A page fails a test if its text outside the frontmatter, code and the attributes of component tags types out by hand a fact, one of the named values the docs render with `<Fact>`, that contains three or more digits in a row (dates aside), a dollar amount or a [bps](/docs/help/glossary#basis-point-bps) value. Tests check most facts against the contracts, the agent and the fork-run gas log. A few cite documents instead: the planned x402 price and the treasury size cite the treasury design spec, and the AMZNc pool liquidity cites the README and that spec. The check count cites that spec too, and its only test compares it with the site's own list of check labels, not with the contract.
- Test counts are not shown, because they go stale. The [Quickstart](/docs/get-started/quickstart) shows how to run the suites yourself.
- The date at the top of each page except the docs home, Last reviewed, says when the page was last checked against its sources.
